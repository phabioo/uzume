# Using the app

At a glance: How to install and use the Uzume app: connect and pair, play, share and watch Sessions, run a server on this PC, collect logs and report problems. Administration of the server is in the app (sidebar item "Server", admins only; server settings under Server › Settings). What it does: [features.md](https://github.com/phabioo/uzume/blob/main/docs/features.md).

Contents: [Install](#install), [Play on this PC and share](#play-on-this-pc-and-share), [Set up a server on this PC](#set-up-a-server-on-this-pc), [Connect and pair](#connect-and-pair), [Play](#play), [Randomize a game](#randomize-a-game), [Plugins (developer mode)](#plugins-developer-mode), [Collect logs](#collect-logs), [Connection check](#connection-check), [Claude debugging (MCP)](#claude-debugging-mcp), [Report a problem](#report-a-problem), [Data directory](#data-directory), [Command line and environment](#command-line-and-environment), [Multiview](#multiview).

Uzume (`client/`, the app) connects to a server, keeps your library and saves in sync, runs games locally and shares or watches Sessions. Feature overview: [features.md](https://github.com/phabioo/uzume/blob/main/docs/features.md). Internals: [app-internals.md](https://github.com/phabioo/uzume/blob/main/docs/reference/app-internals.md).

## Install

- **Windows:** run the installer from the [GitHub releases](https://github.com/phabioo/uzume/releases): the MSI `uzume-<version>-windows-x64.msi` (CI artifact `uzume-windows-x64-msi`); the portable zip works too. The default is a per-user app install, no admin rights. The installer is unsigned (SmartScreen warning). Neither ships an emulator core: the app downloads the core for a system from the server on first use. Installer details: [packaging.md](https://github.com/phabioo/uzume/blob/main/docs/guides/packaging.md).
- **Linux (x86-64):** download `Uzume-<version>-x86_64.AppImage` from the [GitHub releases](https://github.com/phabioo/uzume/releases), make it executable (`chmod +x Uzume-*.AppImage`, or tick "Allow executing as program" in the file manager) and run it. It needs glibc 2.38 or newer (for example Ubuntu 24.04, Fedora 40, current SteamOS) and FUSE 2 (`libfuse2`); without FUSE start it with `APPIMAGE_EXTRACT_AND_RUN=1`. No emulator core inside: the app downloads cores from the server. The AppImage is unsigned. Building for development: [development.md](https://github.com/phabioo/uzume/blob/main/docs/development.md).
- **Steam Deck:** in desktop mode download the AppImage with the browser, run `chmod +x` on it (or via Properties > Permissions), start it once to check, then in Steam choose Add a Game > Add a Non-Steam Game > Browse, select the file and add it. Gamepads reach the app through Steam Input and SDL3 (the app reads them with SDL3, also outside Steam); map the buttons in the app's input settings. Data stays in `~/.local/share/Uzume/Uzume`, so it survives updating or moving the file. Credentials are stored in the freedesktop Secret Service (GNOME Keyring, KWallet, KeePassXC); without a session bus or Secret Service they stay in memory only, so pair again after a restart.

## Play on this PC and share

"Play on this PC" needs no installer rights: the app starts its own server as a child process on this PC only (loopback), keeps its data in the app's folder and stops it when the app closes. It never shares and has no service. "Share with others" (Windows) asks for admin rights once, installs the server as a service and moves your data (accounts, saves, library) over without overwriting anything; the app keeps your pairing. "Stop sharing" stops and disables the service. Accounts and saves stay and the app keeps running them for you alone. "Share again" turns the service back on. See [ADR 0030](https://github.com/phabioo/uzume/blob/main/docs/adr/0030-one-app-one-server-uzume.md) D6.

## Set up a server on this PC

On the connection screen, "Set up a server on this PC" runs a server on the same computer without a pairing code ([ADR 0021](https://github.com/phabioo/uzume/blob/main/docs/adr/0021-one-windows-installer.md)):

1. If no local server is installed, the app downloads the MSI of its own version, checks size and SHA-256 and runs it elevated (UAC prompt) with the server feature. The app then moves to Program Files; its data is copied once from the old portable folder and never overwritten.
2. You choose an admin name and password; the app creates the first admin and pairs over localhost. The certificate is trusted automatically only for `127.0.0.1` on the registered port. With an existing local server, "Connect" asks for an admin's credentials instead.
3. Network sharing starts off, so the server listens only on this PC. Pick a ROM folder (the server's import folder; the app asks for admin rights once to give the server service read access) and "Rescan" in Server › Games. Switch "Network sharing" on under Settings > servers ("This PC's server") or in Server › Settings › Network & sharing to let other apps connect. Cores come from the libretro buildbot through this server.

## Connect and pair

1. Start the app. On the first start choose "Play on this PC", "Join a server" or "Set up a server". For "Join a server" enter the server address or paste an invite link (`uzume://join/server.example.com:8443/UZ-XXXX-XXXX#...`; Ctrl+V works on the start screen, clicking a link opens the running app). A bare invite code (`UZ-XXXX-XXXX`) does not name its server, so the app asks for the address next. Uzume connects automatically on later starts once a connection succeeded; turn it off in Settings › Servers.
2. The app shows a security code (`K7Q4-9WMP-2HXD`). Compare it with the code on the server's screen or `uzume-server code`, then continue (trust on first use). With an invite link the app checks the certificate fingerprint in the link itself. On a mismatch the app stops and sends no invite, password or setup code. The SHA-256 fingerprint stays available under Details.
3. Sign in with your user name and password, or use your invite code with a display name (and optionally a password). Without a password, ask an admin to allow the device under Server › People › Devices. A server without an admin is set up with its setup code (printed at first start, or `uzume-server setup-code`).
4. Several people can use one PC: the people sheet (Ctrl+Shift+U) switches the user, adds a person or removes one from this PC. An optional 4-digit PIN for this PC protects switching; it stays on this PC, and after 3 wrong PINs the password is needed. "My account" changes name, password and PIN and lists your devices. It also has the switch "Show what I play on Discord" (off by default): while a game runs, your Discord profile shows its title, the system and "Session" or the run name ([features](https://github.com/phabioo/uzume/blob/main/docs/features.md#discord-rich-presence)). Forgotten password: an admin resets it; admins use `uzume-server reset-admin` on the server.
5. Credentials are stored in the Windows Credential Manager under the target `Uzume/<server id>/<device id>` (PIN hashes under `Uzume/pin/<server id>/<device id>`). On Linux the same targets live in the Secret Service (default collection, attributes `application=uzume`, `uzume-target=<target>`). Known limitation: macOS and Linux without a Secret Service (no session bus, for example headless) have no OS credential store; the device credential is kept in memory only, so after every restart the app signs in again (no secret is written to disk).

After a server certificate change (renewal) the server card shows the stored and the presented fingerprint. "Trust new certificate", then "Yes, trust this certificate" re-pins it and keeps the credential (CLI: `--accept-fingerprint <sha256>`). Settings → Hubs switches, edits (address, port), removes and sets auto-connect for servers.

## Play

- The Library lists the server's games with search and filter chips; a game opens its game page (tabs Overview, Saves, Settings, Manage). ROMs are downloaded into a hash-verified, resumable cache. Start a game; the app fetches the core on demand (shown as core loading / missing / incompatible).
- Favourites and collections: the game page has a "Favourite" button, shows play time, last played and sessions, and "Add to collection" lists your collections. In the Library the chips All / Favourites / your collections filter the list, "+ Collection" creates one (deleting a collection keeps its games), and the sort picks Recently played, Name or Play time. Users and runs show play time. Everything is stored per user on the server.
- If the server allows user uploads, "Add games…" in the Library header adds your own (homebrew or own-dump) ROMs. An uploaded ROM is kept in the local ROM cache, so it starts without downloading.
- Library folders (0.12, [guide](Local-ROMs)): Settings → Library folders adds folders with your own ROMs. They are scanned, registered with the server and started straight from the folder. The Library marks games that are not on the server as **Local** and games without a file on this device as **Missing**. "Upload to Hub" in the game detail (and "Add games…") sends a file in resumable chunks; it continues after a restart. "Remove from library" drops your registration of a local-only game (saves stay).
- Firmware (NDS): in native firmware mode the app fetches the firmware files the admin provided and shows "Firmware required" / "Firmware missing" instead of launching without them.
- Keyboard: Arrows, X=A, Z=B, S=X, A=Y, Q=L, W=R, Enter=Start, Tab=Select, Esc=Pause (always, in a window and in fullscreen; it opens the Quick menu, see below), F11 toggles fullscreen, F3 diagnostics, Space speed-up, + / − volume, M mute, F7 screen layout menu (Shift+F7 swaps the screens; NDS and 3DS), F6 save state (Shift+F6 next slot), F8 load state, Backspace (hold) rewind; the app keys are configurable in Controllers > Hotkeys). Mouse = DS touch. Gamepads and remapping: Controllers page.
- Gamepad hotkeys (P1): Controllers > Hotkeys has a "Gamepad" column next to the key. A gamepad hotkey is the hotkey button (default Select, change it with "Gamepad hotkey button") held plus a second button. Defaults (0.14): the Uzume hotkeys get Select + a button, for example Select+RT (R2) speed-up, Select+RB save state, Select+LB load state, Select+LT (hold) rewind, Select+D-Pad left diagnostics (Select+R3 is push-to-talk), Select+B fullscreen, Select+D-pad up/down volume, Select+X mute, Select+Right next screen layout (exact list: Controllers > Hotkeys); plugin hotkeys have no gamepad default. A conflict is shown on the row and the Uzume key wins. Click a field and press the combo (hold the hotkey button first); pressing a button alone binds that single button without the hotkey button (use a spare button). A button used by another hotkey or the hotkey button is refused. x clears, Reset restores the default. The combo button is never sent to the game; the hotkey button itself still is (Select works as in the game while you hold it). A button that was already held when you pressed the hotkey button does not trigger anything. Game screen hints show the gamepad combo while a gamepad was the last input you used, else the key.
- Volume and sound: + / − (or Select + D-pad up/down) change the volume, M (or Select + X) mutes; volume keys repeat while held, other app hotkeys do not, and volume up while muted unmutes. The header "Sound" control (it shows the volume, for example "5 %") opens the "Sound" popover with the sliders "My game" (master volume), "Voice" and "Plugin sounds" (Up / Down move to the next slider, Left / Right change it, B closes), "Muted in the background", "Mute all" / "Unmute" and "Sound settings" (leaves the game view to the background and opens Settings). Settings › This PC › Audio & video holds Output, Mute when in the background, Volume steps and Show volume on screen. Volume and mute affect only what you hear, not the Session you share.
- Screenshots: F12 (or Select + Y) takes a screenshot of the running game, also in the game's "⋯" menu, the Quick menu and the Game tab ("Screenshot"). It goes to your server (tagged with the run when the game runs in a run) and shows as the "Screenshots (N)" strip on the game page, with a viewer (Previous / Next, "Save as...", "Delete..."). Until the server has it, the picture waits in `<data>/screenshots/pending/` (PNG plus a small JSON file) and uploads with the next connection; the game says "Screenshot saved on this PC. It uploads when the server is back." A picture the server refuses (not a valid image, over 16 MiB) is dropped with a line in the log.
- Quick menu: Esc, the Pause button and Start on a pad pause the game and open the Quick menu over the stage (the header and the panel stay). It offers Resume, the groups Game (Save snapshot, Manage saves…, Screenshot, Settings for this game…, Reset game…), Play, Together and Help, and Quit game…. Up / Down and Left / Right move, Enter or pad A chooses, Esc or pad B resumes.
- Speed-up: Space, configurable in Controllers > Hotkeys (or the header split button "» Speed-up", which shows "OFF · 2×" or the running speed) runs the game faster. The speed part of the button opens a menu with 1.5×, 2×, 3×, 4×, 6× or 8× for the running game (narrow windows show only "»" and the value). Emulation page settings (global, system or game): "Speed-up speed" (default 2×), "Speed-up on start" (default off; the game starts sped up and stays so until toggled) and "Audio during speed-up" (default on: audio is resampled, so the pitch rises; off mutes it). The button is hidden if the core does not allow it. It also works while your Session is shared; viewers see the sped-up game at the normal frame rate (audio follows the same setting). Saves sync as usual.
- Core choice ([ADR 0020](https://github.com/phabioo/uzume/blob/main/docs/adr/0020-cores-from-the-libretro-buildbot.md)): the server admin installs the cores; the Emulation page offers a "Core" select per system with the cores the server serves. The effective core is game > system > server default; a stored choice the server no longer serves is ignored with a notice. Per game the select offers "Use system default" or a core of the system (0.10). Core options stay per core.
- Experimental cores: a core without an Uzume profile (badge "experimental") runs without option defaults or locks, shows the framebuffer as one screen, has no touch input and only gets firmware placed in its system directory.
- Core change and saves: when a game starts with another core or another build than the one that last wrote its save, the app first creates a manual snapshot on the server ("Before core change: ..." in the save history) and shows a notice. If the snapshot cannot be created (server unreachable) the game does not start and the save stays untouched; without server snapshot support a local backup copy is made. Switch back to the previous core to start offline.
- Save files per core: the server always holds the raw cartridge save. melonDS DS stores it as `<game>.sav`; DeSmuME keeps its own `<game>.dsv` (raw save plus a DeSmuME footer), which the app converts before the start and after play. Only the file of the running core is synced, so switching cores never flips the server save between formats. A `.dsv` that cannot be read is never uploaded and never overwritten; the game reports it and your server save stays unchanged.
- Emulation page: core options per global / system level (options Uzume controls are hidden). melonDS DS offers an OpenGL renderer and internal resolution (applied on next start; default Software). `UZUME_DISABLE_HW_RENDER=1` forces the software path.
- Renderer (0.24): systems whose core offers both, today 3DS (Azahar), get a "Renderer" row (OpenGL | Vulkan, default OpenGL, tag "Next start") in Settings › Emulation and, per game, on the Core tab of the game settings. It is stored as `uzume.renderer` (system or game level; reset removes it) and applies from the next game start. melonDS DS (OpenGL only) and software cores such as mGBA have no Renderer row; the Defaults tab has none either.
- Game overrides (0.10): Settings › Emulation › Game overrides lists the games with changed settings and opens the game page's Settings tab, which edits them at Game level (game > system > global).
- Per-game settings (0.19): the game page's Settings tab or in game "⋯" > "Settings for this game…". Tabs Picture, Controls, Speed-up, Core; a row reads "Uses your default (X)" or "Changed for this game" and has its own reset, "Reset all" clears the game. Integer scaling and Aspect ratio change live, the rest applies from the next start. Controls picks a controller profile for player 1's gamepad and for the keyboard while this game runs (also Emulation page, system or game level); it does not change the device assignment, and a deleted profile shows as missing and the device's own profile is used.
- Save states (0.20): a state is the core's snapshot of the running game, kept per game and save slot in slots A (Auto) and 1 to 4; it is never your save (saves change only when the game saves). F6 saves into the current slot, Shift+F6 moves to the next slot, F8 loads it; the in-game Saves tab and the game page Saves tab list the slots with a preview, time and core version and offer Save to N, Load N and Delete. Loading asks first (Load / Cancel; "Don't ask again" turns the question off) and keeps the progress before the load in Auto; the toast has Undo for 6 seconds. A state saved with an older core version carries the tag "Older core" and the button reads "Try to load"; a state of another core is refused. With a server that has `states_v1` states are uploaded after saving and listed from the server, a state not on this PC is downloaded when you load it; offline they stay on this PC and upload later. Settings › This PC › Storage shows "Save states" and offers to remove states of deleted games. In a run, `rules.states` and `rules.rewind` decide ("Save states are off in this run · rule set by <name>", "Rewind is off in this run"), live when the rules change; loading a state in a run is logged as `state.loaded`.
- Rewind and run-ahead (0.20): hold Backspace (gamepad Select+LT) to play backwards at about four times the speed, with the toast "Rewinding · N s left"; the sound is muted meanwhile. Emulation settings › "Rewind": "Rewind length" (off by default; shows the estimated memory) and "Run-ahead" (0, 1 or 2 frames, only for cores that allow it, never for the 3DS). Both are off for cores without save-state support.
- Hold-Select sheet: hold the gamepad hotkey button (default Select) alone for about 400 ms in a running game to see the current gamepad hotkeys over the game; release or press another button to hide it, hotkeys work as before.
- Nintendo 3DS ([ADR 0022](https://github.com/phabioo/uzume/blob/main/docs/adr/0022-nintendo-3ds-with-azahar.md)): needs the `azahar` core installed by the server admin and an OpenGL Core >= 3.3 context; without it the game does not start and the app shows an error (no software fallback; `UZUME_DISABLE_HW_RENDER=1` therefore also blocks 3DS games). Use decrypted dumps (`.3ds .cci .cxi .3dsx` and the compressed `.zcci .zcxi .z3dsx`); Uzume never decrypts and ships no firmware. Layout: top 400x240, bottom 320x240 with touch by mouse. Keyboard: E/R = ZL/ZR, T/G/F/H = circle pad, I/K/J/L = C-stick. Gamepad: triggers = ZL/ZR, left stick = circle pad (the DS folds them back into L/R and the D-pad). Earlier user profiles keep their bindings; set the new inputs manually in Controllers.
- Game Boy, Game Boy Color and Game Boy Advance ([ADR 0024](https://github.com/phabioo/uzume/blob/main/docs/adr/0024-system-template-and-game-boy.md)): the server admin installs a core (for example mGBA, or Gambatte for GB/GBC). Extensions `.gb`, `.gbc`, `.gba`; one screen. A boot ROM/BIOS is optional and used only in firmware mode `native`. Keyboard and gamepad use the same bindings as other systems; L/R exist only on the GBA.
- 3DS saves sync with the server like other saves (the game's save data and extdata only, not system data). Restore, upload and conflict resolution in a running 3DS game restart the game with the new save (as for NDS).
- ROM cache: Settings → "ROM cache limit" (default 20 GB, 0 = unlimited). The least recently used ROMs are removed first; the running or starting game, active downloads and `.part` files are never removed. Trimming runs at startup, when a ROM is ready, when a game ends and when the limit changes. "Clear ROM cache" asks for confirmation and shows the freed size. Settings › This PC › Storage shows what the app keeps on this PC and offers clean-ups (games not played in 60 days, older core versions); each asks first, and saves are never offered.
- Settings: Appearance (Dark / Light / System, Text size 100 % / 125 % / TV, Reduce motion), Updates (channel, automatic install), Hubs.
- Gamepad outside the game: D-pad or left stick moves, A chooses, B goes back one level, Y focuses search (Library, Emulation), L / R switch the Library status filter. The hint row at the bottom shows these while a gamepad was the last input. Esc does the same as B on the keyboard.

### Online list and notifications

- **Who is online**: the ONLINE group in the side menu lists the people on your server. Click "Watch" next to someone who shares a Session; click "Invite" to invite them to your shared Session or to the run you play. Hidden when you play only on this PC.
- **Bell**: the bell at the top of the side menu shows how many news are unread. Click it to read them (this marks them read); click an entry to act (Watch, Open run, What's new, Open status). The list keeps the last 50 entries until you switch server or quit.
- **Toasts and sound**: Settings › This PC › Notifications sets per kind (Invites, Sessions started, Run events, Updates, Server problems for admins) whether it also shows as a toast or only waits in the bell. "Quiet in fullscreen" (default on) lets only mentions toast while a game is fullscreen; "Sound for toasts" plays a short chime.

### Ready check and pause for everyone

- **Ready check…** (in the "⋯" menu and the Quick menu, group Together): one click asks everyone in your run, or in the Session you share or watch, whether they are ready. A card on the stage lists each person as Waiting, Ready or Not yet and counts down 30 seconds. Answer with the Ready / Not yet buttons, the keys 1 / 2 or the pad (A = Ready, B = Not yet; the game still gets the button). You can cancel a check you started. When everybody is ready you see "Everyone is ready". On the board of an active run the same card and a "Ready check" button are in the Runs screen.
- **Pause for everyone** (Shift+Esc, or the same menu entry): pauses the game of every member of the run (in a Session: the host's game). A toast "<name> paused for everyone" stays with **Resume** until someone resumes; Esc does not open the Quick menu meanwhile. A game you had paused yourself is not resumed by it.

### Chat and the panel tabs

- **Tabs**: the panel beside the game has Session · People · Chat · Saves (in a run Run · Chat · Saves). Alt+1 … Alt+9 open tab 1 … 9 while the game has the keys. Saves holds the save list and the states; People lists who is in the Session with Host / Viewer, how each person is connected and which quality they get (see **Quality** below); Run shows the run and who joined.
- **Quality** (viewer): when you watch a Session, your own row in the People tab has Quality: Auto · High · Medium · Low. Auto adapts to your connection (the default); High is 4 Mbit/s, Medium 1.5 Mbit/s and Low 0.6 Mbit/s at 30 frames per second, for weak connections. One click switches, the picture keeps running, and the choice is remembered on this PC for the next Sessions you watch. Rows read "Direct · 18 ms · gets High" (Direct or Relayed, latency, the quality received) or "Relayed · 60 ms · picked Medium". As host you see the same line for each viewer and "Sending 2 streams · 3.1 Mbit/s" under the list; viewers only watch, chat and talk, they never control your game. F3 shows the same under Stream.
- **Chat**: open the Chat tab (Alt+3), type, press Enter. It talks to your run, or to the Session you share or watch. `@name` pings a person (spaces in a display name may be left out); the three buttons send Down!, Gym next and Wait (Alt+1 / 2 / 3 while you are typing). Esc gives the keys back to the game. :gg: :wave: :lol: :hype: :sad: :ok: turn into 🎮 👋 😂 🔥 😢 👍. Run chat is kept by the server, so it is still there when you come back; Session chat ends with the Session.
- **Unread and pings**: the Chat tab shows how many messages came in while it was closed (a dot when many tabs are shown). Only a message that names you pops up as a toast and waits in the bell; plain messages stay quiet.

### Controller hand-over

- **Ask**: watching a friend's Session, open the **People** tab and click **Take over P1** on your own row (or **Play as P2** when the game has two controller ports; the Nintendo DS and 3DS have one). The row reads "Asked lena…" while you wait; **Cancel** withdraws it.
- **Confirm**: the host sees a card on the stage, "max wants to play as P2", with **Allow** (key **1**) and **Deny** (key **2**); without an answer it is denied after 20 seconds. Nothing is shared without that click.
- **Play**: once allowed you are a **PLAYER** (the tag reads "PLAYER P2" for everybody). Click your tile so it has the focus: your keyboard (your keyboard profile), gamepad and, with P1 on a DS game, the mouse on the bottom screen now play on the host's game. Hotkeys and Esc stay yours. **Stop playing** gives it back.
- **Take back**: the host clicks **Take back** on the card or on your People row, or presses **Esc twice**. While you hold P1 the host's own P1 keyboard and pad are off (host hotkeys still work). If you leave or the connection drops, the controller goes back at once. Only one person can hold a port; the next request reads "P1 is taken".
- Input goes straight between the apps (second data channel, the server is not involved); with a slow connection a button may feel late, and after half a second without input from you the port is released to "nothing pressed" until you press again.

### Voice chat

- **Join**: when your run or Session has a voice room, the header shows **Join voice** (also in the People tab and the "⋯" menu). Runs you play and invite-only Sessions join by themselves (Settings › This PC › Voice › Join voice automatically); **Leave voice** is one click in the People tab. Up to 8 people; a full room says so. Voice goes directly between the apps; the server only introduces them, and nothing is recorded.
- **Talking**: push-to-talk is the default: hold **V** (or hold Select + R3 on a pad); the header reads "Hold V" and "Live" while you talk, with the speaking bars next to your name. **Shift+M** switches your microphone off and on ("Mic off": others see a mic-off mark). With **Voice activation** the microphone is live and sends while you speak above the line set under Settings › This PC › Voice; V and Select + R3 then switch the microphone instead. Headphones keep the game out of the microphone; noise suppression and echo cancellation help when you use speakers.
- **Marks**: in People (and on the Multiview tiles) a person who speaks has three bars, one with the microphone off a crossed mic, one who was muted by the host a filled crossed mic and the words MUTED BY HOST. Every other person has a **Volume** slider on their row; it is remembered per person. The owner of a Session has **Mute** on each row (it holds for the whole Session and only the host can undo it).
- **When it does not work**: "No microphone" means none was found (you can still listen; plug one in and click the control), "Blocked" means the system refuses the microphone (Windows: Settings › Privacy › Microphone, button **Open Windows settings**; Linux: allow it in the PipeWire prompt and click **Try again**).
- **Settings › This PC › Voice**: Microphone (the level bar shows what it hears; click the bar to set the voice-activation line), Talk, the push-to-talk key (change under Hotkeys), Noise suppression, **Lower game volume while someone speaks** (halves game and watched tiles) and **Join voice automatically**. The Sound popover's **Voice** slider sets the volume of everyone's voice.

Saves sync automatically; see [saves.md](Saves). Sharing and watching: [sessions-over-the-internet.md](Sessions-over-the-internet).

## Randomize a game

Since 0.21 ([ADR 0031](https://github.com/phabioo/uzume/blob/main/docs/adr/0031-game-variants-and-randomizer.md), behaviour: [features.md](https://github.com/phabioo/uzume/blob/main/docs/features.md#game-variants-and-the-randomizer)). You play a randomized copy of a game in its own save slot; Main and the original game stay untouched. Needs the plugin Randomizer (enabled; official, or a local copy with Developer mode on) and a server that offers the randomizer engine.

1. **Server side (admin, once):** Server › Tools shows the engine (UPR FVX, GPL-3.0). "Get the engine" downloads a release for all platforms, "Offer to apps" turns it on for the apps; without a source use `uzume-server import-tools` ([server guide](Server-configuration#tools)). Nothing is offered until an admin turns it on.
2. **Randomize:** open the game page and choose Randomize… next to Play (it is off with a reason for games the plugin does not support, and missing without the plugin). Pick a preset or "Custom" and paste a settings string, optionally set a seed (off: a random one) and "Keep a spoiler log", and name the variant (up to 60 characters, unique per game). The dialog shows the slot the variant will play in.
3. **First time on this PC:** if the engine is not on this PC, "Download and build" fetches it from your server (size and SHA-256 are checked; it is a Java runtime with the engine, up to 400 MB, downloaded once into `<data>/cache/tools/`). If the server offers no engine or is offline, the dialog says so and, for admins, links to Server › Tools.
4. **Build:** reading the game file, randomizing, writing; small games (GB, GBC, GBA) build in the background with the button reading "Building…", larger ones show a progress dialog with "Run in background" and Cancel (cancelling keeps nothing; quitting while building asks first and the build starts over next time). A 3DS game runs the engine with a 4 GB Java heap (the build checks that about three quarters of it is free) and takes up to 15 minutes at most; other games get 1 GB and 3 minutes. If your game file is a different dump than the recipe pins, the variant shows what it expected and "Build anyway".
5. **Play and manage:** the game page has a Variants section with each variant's preset, slot and status (Play, Rebuild, Rename…, Copy seed and settings, Open spoiler log…, Delete…). Deleting asks whether to keep the saves (default; the recipe stays so you can build it again) or delete the slot too. The slot picker lists Main and the variants; a library row shows how many variants a game has. The spoiler log opens only after a confirm and is never shown in game or to others.
6. **Runs:** in New run choose the Randomizer section ("Each person gets their own" or "Same world for everyone", preset or custom string, "Allow own variants"). Everyone joining builds their own copy on their own PC before the first start ("Building your variant"); with "Allow own variants" you may instead bring one of your variants of the same game that uses the run's engine version. The run's spoiler log opens from Saves only after the run ends, and only your own.
7. **Storage:** Settings › Folders & storage › Variants shows the built copies in `<data>/cache/variants/` (default limit 8 GB, least recently played go first), "Free space" and "Remove variants not played for 30/60/90 days". Only the copies on this PC go; recipes and saves stay on the server, and a variant rebuilds from its recipe the next time you play it.

3DS variants are a LayeredFS folder that the app places in the Azahar folder of the variant's slot; 3DS game updates are not handled yet (open).

## Plugins (developer mode)

Plugin runtime of 0.11 ([API reference](https://github.com/phabioo/uzume/blob/main/docs/guides/plugin-api.md), [design](https://github.com/phabioo/uzume/blob/main/docs/architecture/12-plugins.md)); plugins have no on-screen UI yet.

- Settings → Plugins: turn on "Developer mode". Plugins (all unsigned, local) run only while it is on and are resolved once when a game starts.
- "Install from folder…" copies a plugin folder (with `manifest.json`) into `<data>/plugins/installed/`; "Link folder for development…" runs the plugin straight from your folder and reloads it when you save a file. The list has an on/off switch and Uninstall per plugin.
- Settings → Plugins → "Plugin language": Auto (default), English or Deutsch. Auto uses the 3DS system language (Azahar core option) for 3DS games, otherwise the language of your computer. Applies when the next game starts.
- Plugin console: a tab in the running game (developer mode only) with watched values, events, log and the core's memory map regions; Ctrl+Shift+R reloads the plugins. A plugin that fails or exceeds its budget is paused alone; the game keeps running.

## Collect logs

When something does not work, hand over one file instead of describing it: Settings → Diagnostics → "Collect logs…" opens a save dialog (default name `uzume-diagnostics-<UTC timestamp>.zip` in Desktop or Downloads) and writes the bundle in the background; "Show in folder" then opens its folder. Without the window (for example when the app does not start): `Uzume --collect-logs out.zip [--data-dir <path>]` (offline, reads only the data directory, refuses to overwrite an existing file). Same layout as the server bundle ([server-configuration.md](Server-configuration)):

| Entry | Content |
|---|---|
| `README.txt` | what is in the bundle and what was removed |
| `player-info.json` | `info_version` 1, time; app version, channel, commit, protocol; OS, architecture, CPU threads, Qt version, data directory, portable or not, free space; saved servers with name, address, server version, connected and features (no tokens); cores per system with versions, hardware rendering on/off; available H.264 encoders and the one last used for sharing; connected gamepads; non-secret settings (update channel, automatic install, developer mode, ROM cache limit, force relay, GPU encode switch) |
| `logs/player.log`, `logs/player.1.log` ... | the app's log files in `<data>/logs/`, newest first, capped at 50 MiB in total (the oldest file that does not fit is cut to its newest lines at a line boundary, marked with `[older content cut: size cap of the bundle]`) |
| `logs/plugins/...` | plugin console logs, when they exist on disk in `<data>/logs/plugins/` |
| `connection-check.json` | only when you pressed "Add to problem report" in the [connection check](#connection-check) since the last bundle: steps, states, texts, NAT type |

Redacted before packing: credentials, device tokens, TURN `username`/`credential`, invite codes, `Authorization`/`Bearer` values and cookies become `[redacted]`. ## Connection check

When Sessions only work on your home network, or lag more than they should, run Settings → Hubs → "Connection check…" (or Settings → Diagnostics → "Run check…"). The dialog checks five steps in order against the active server and ends with a plain-language result:

| Step | What it does | Result rows |
|---|---|---|
| Server reachable | HTTPS request to the server's info endpoint with the pinned certificate; latency | failed: no answer, name not found, port refused, certificate does not match, not a server |
| STUN | binding requests from one UDP socket to the STUN servers the server hands out (and to the relay's own STUN port); finds your public address | none handed out: skipped; none answered: failed |
| TURN relay | allocates on the server's relay with the short-lived credentials the server handed out, then frees it again | Server has TURN off: skipped; refused credentials / no answer: failed |
| NAT type | compares the public address and port that two different STUN servers saw for the same socket: same = open (endpoint-independent), different = symmetric NAT (amber) | needs two answers, otherwise "Not determined" |
| Test connection | two WebRTC peers inside the app connect through the server's ICE servers and echo a few messages; with a symmetric NAT or no STUN answer they may use the relay only | see below |

What the test connection proves: the app's WebRTC stack works with these servers and found a public address (candidate counts are in the exported result); when the relay is needed, data really flows through the server's relay (allocation, permission and forwarding), with the measured round-trip time. It does not prove that a direct path to another app works: that also depends on the other app's network (the server has no WebRTC peer to test against), so "direct connections possible" is an estimate from STUN, NAT type and the test.

Results: "Your network allows direct connections" (green), "Only relayed connections are possible here" (amber: works, adds delay), "Connections to other networks are not possible from here" (amber: no usable relay or STUN, so Sessions work on the same network only), "<Hub> cannot be reached" (the other steps are skipped; "Edit server address…" opens the server's address field in Settings). If the app has no open session with the server, the check ends after step 1 with "Connect to <server> to run the full check", because the server's STUN and relay servers are not known then. A check can be cancelled (Esc or Cancel) and stops after 60 s at the latest.

Actions: "Copy result" (Ctrl+C) copies the result as text, "Add to problem report" keeps it for the next "Collect logs" bundle (`connection-check.json`, taken by that one bundle) and ticks it in the "Report a problem" dialog (until a report with it was sent), "Run again" (R). The text and the JSON contain addresses and server names, never the relay credentials. `UZUME_FORCE_RELAY=1` is noted in the result and makes the check report "only relayed".

## Claude debugging (MCP)

For developers: the app can embed a local [MCP](https://modelcontextprotocol.io) server so a Claude Code session on the same PC reads and controls the app, its plugins and the running game ([ADR 0032](https://github.com/phabioo/uzume/blob/main/docs/adr/0032-debug-mcp-server.md)). It is off by default, also in release builds.

1. Settings › Diagnostics › Claude debugging (MCP): turn on "Allow Claude to control this app" (or start the app with `--mcp`). The port is 47615 unless you change it (1024 to 65535).
2. "Copy setup command" and run it in Claude Code on this PC: `claude mcp add --transport http uzume http://127.0.0.1:<port>/mcp --header "Authorization: Bearer <token>"`. "New token" replaces the token at once. The token is random, lives only in the OS credential store (target `Uzume/mcp`) and is never written to a file or the log.
3. `--mcp-port <n>` sets the port for this start only. With `--mcp`, the environment variable `UZUME_MCP_TOKEN` (32 to 256 characters of `A-Z a-z 0-9 - _`) is the token for this start instead of the credential store; it is never stored or logged and is ignored without `--mcp`.
4. While the server listens, a band "Claude can control this app" with a "Stop" button shows at the bottom of every screen, the game included.

The server binds to `127.0.0.1` only, checks the token, the `Host` header and (if present) a loopback `Origin`, and takes `POST /mcp` with bodies up to 1 MiB. Every call is logged as `mcp: <tool> <target>`, never with arguments or results.

The UI tools act like a person at the keyboard, with one exception: a destructive control is never operated. `ui_click`, and `ui_key` or `ui_type` with Return, Enter or Space on it, answer `needs_confirmation_in_app` and the refusal is logged (`mcp: refused ui_click needs_confirmation_in_app <objectName>`). A test run (app started with `UZUME_MCP_CONFIRM=1`) can pass `confirm: true` to `ui_click`, `ui_type` or `ui_key` to operate such a control; without the variable the refusal stays. Destructive are danger buttons (`kind: "danger"`, the `destructive` property of `UzButton`), and buttons for deleting, removing, restoring or overwriting, "Share with others", "Stop sharing", installs and updates (which can need admin rights); "New token" and turning the server off are allowed. The match is deliberately wide: it also covers "Remove" of a library folder. `ui_tree` marks such controls with `destructive: true`. Password fields (and fields of a component with `secret`) show `***` instead of their text in `ui_tree`, in the answers of `ui_type` and in text search; typing into them is allowed. A screenshot shows what the screen shows, so do not reveal a password while Claude looks. Known limit: a control that is destructive but not marked or named as above is not recognised, so mark new ones with `destructive: true`. Game data goes only to your Claude session on this PC.

## Report a problem

Settings → Diagnostics → "Report a problem…" (and "Report a problem…" in the in-game "⋯" menu) opens a dialog: describe what happened in a few words and send it, with a few attachments, to your own Uzume server. The admins of that server see it in their report list; nothing goes to anyone else. Ctrl+Enter sends, Esc cancels.

| Attachment | Default | Content |
|---|---|---|
| Logs of the last 3 days | on | `player-logs.txt`, redacted like "Collect logs", cut to the newest lines if large |
| Settings | on | `settings.json`, redacted, no passwords and no server token |
| Connection check | off; on when you pressed "Add to problem report" in the connection check. Listed as "Connection check from <time>" whenever a result exists | `connection-check.json` |
| System info | off | `system-info.json`: OS, GPU, driver, cores |

"See what is included" lists the file names. Never included: passwords, the server pairing token, ROMs, saves. The server allows 25 MB per report (uncheck the logs when it is larger) and 5 reports per device and hour.

While it uploads, the dialog shows progress and "Cancel" (back to editing, the text is kept). It then shows "Sent. Report #<number>". If the server is offline, the dialog says so and sends the report by itself as soon as the server is reachable again, as long as the dialog stays open; "Save as file…" writes the same zip (`report.txt` with your text, plus the checked files) so you can pass it on yourself. If the upload fails, the text is kept and "Try again" repeats it. A server without the `reports_v1` feature (older than 0.17) cannot receive reports; use "Save as file…" or "Collect logs…".

## Data directory

The ROM cache, `profiles.json`, `device.json`, `hubs/<id>/users/<user_id>/saves/<game_id>/`, `system/` and settings are stored portable by default in `<directory of the executable>/data` (plugins in `plugins/`, the randomizer engine in `cache/tools/`, built variants in `cache/variants/`), provided a real write test succeeds there. Otherwise the app falls back to AppData (`QStandardPaths::AppDataLocation`) and logs a note, for example when installed under Program Files. On Linux (AppImage) the data is in `~/.local/share/Uzume/Uzume` (`$XDG_DATA_HOME/Uzume/Uzume`): the launcher of the image sets `UZUME_DATA_DIR` to it, so it never depends on where the file is. On the first portable start existing AppData data is copied once (nothing is moved, deleted or overwritten; `device_id` is preserved; the ROM cache is re-downloaded). Credentials stay in the OS credential store. `--data-dir <path>` or `UZUME_DATA_DIR` take precedence ([ADR 0004](https://github.com/phabioo/uzume/blob/main/docs/adr/0004-player-portable-data.md)).

## Command line and environment

```sh
uzume [--data-dir <path>] [--mcp [--mcp-port <n>]] [--dev-allow-http] [--collect-logs <out.zip>] [--version | --version-json] [--help]
uzume-cli <command> ...            # run without arguments for the usage text
```

`--mcp` switches [Claude debugging](#claude-debugging-mcp) on for this start only (the setting stays off). `--dev-allow-http` allows HTTP servers outside localhost (development only). The CLI covers `identify`, `pair`, `redeem-invite <address> --code FB-XXXX-XXXX --name <name>`, `games`, `fetch-rom`, `game upload <file> [--title T]`, `systems`, `fetch-core <system-id>`, `saves list`, `save push|pull|resolve`, `session-share --synthetic`, `session-watch` (both accept `--force-relay`) and `update-check`; the CLI has no hardware rendering. `scripts/e2e-player-hub.sh` checks the CLI against a locally built server, including a save round trip.

## Multiview

Sound: the header button "Mixer" (watching, next to "Add tile") opens a popover with one slider per watched person, led by the person square, and the toggle "Mix all tiles". Off (default) you hear exactly one tile, the one with the AUDIO tag ("Audio here"); on, every tile and your own game are mixed, each at its own level, and all carry the AUDIO tag. The levels and the toggle are remembered per person (user id) on this PC; the master volume, mute and "Muted in the background" apply as before. Layouts: PiP (the picture-in-picture tile sits inside the main tile), Row for 2-3 Sessions and Grid 2x2 from 4 Sessions (disabled below 4; no empty slot). "Side by side" now only names the DS screen layout. Diagnostics are docked next to the tiles and float only in fullscreen. When a host pauses, viewers see "Paused by <name>" on the frozen tile ([protocol](https://github.com/phabioo/uzume/blob/main/protocol/datachannel.md)); a host older than 0.14 sends no such state. The fullscreen toolbar has a Pause button. Settings > Updates offers the channel Off | Stable | Beta ([updates](Updates)).
