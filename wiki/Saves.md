# How saves work

At a glance: How saves are stored and synced: the server keeps versioned copies, the app syncs before launch, while playing and on exit, and conflicts are never resolved silently. Covers sync, conflicts, history, restore, snapshots and slots. Administration: Saves tab › All users in the app.

Contents: [Sync](#sync), [Conflicts](#conflicts), [History, restore, snapshots, slots](#history-restore-snapshots-slots).

The server keeps the central, versioned copy of every save; the app syncs with it. The server stores a save as an opaque blob and never merges it. Decisions: [ADR 0005](https://github.com/phabioo/uzume/blob/main/docs/adr/0005-saves-phase3.md), [ADR 0012](https://github.com/phabioo/uzume/blob/main/docs/adr/0012-internet-sessions-and-save-comfort.md) D7; model: [03-saves.md](https://github.com/phabioo/uzume/blob/main/docs/architecture/03-saves.md).

## Sync

- The core writes its battery save to the app's local save directory (melonDS DS: `<rom sha256>.sav`).
- Before launch the app compares the local save with the server's current checkpoint: it downloads a newer server save, uploads a changed local one, or starts empty.
- While playing, changes are uploaded as checkpoints (12 s after the last change, at most every 60 s); on pause, stop and exit a final upload follows. Every upload names the server revision it is based on.
- Without a connection the game starts with the local save and the upload stays pending for the same server and user. Saves are never sent to another server.
- Locations: app `<data dir>/hubs/<hub_id>/users/<user_id>/saves/<game_id>/`; server `<data dir>/saves/` (files; SQLite holds metadata only).

Save source `none` (no sync) exists for systems that keep their data local-only; no system uses it at the moment.

Game Boy, Game Boy Color and Game Boy Advance saves are the core's `SAVE_RAM` as `<game>.sav`, handled like melonDS DS.

Nintendo 3DS (Azahar, save source `core_tree`, format `azahar_sdmc`, [ADR 0022](https://github.com/phabioo/uzume/blob/main/docs/adr/0022-nintendo-3ds-with-azahar.md) D3 amendment): Azahar keeps a virtual SD/NAND tree in the per-slot short dir `<data>/c/<16 hex>/Azahar/`. The app packs only the game's save data (`sdmc/Nintendo 3DS/<id0>/<id1>/title/<high>/<low>/data/**` and `.../extdata/**`) into one deterministic, uncompressed tar, which is the slot's save on the server (opaque, 64 MiB limit; revisions, history, snapshots, conflicts and restore as above). Never synced: `nand/`, `sysdata/`, `shaders/`, `cheats/`, installed content.
- Like DeSmuME `.dsv`, the tar is imported from the tree at start, during play and at the final sync, and exported into the tree before the core starts.
- Before the tree is replaced by a different server version, it is written as `<slot dir>/<rom>.sav.tree-<timestamp>.bak`. Unmanaged files are never touched; an invalid archive blocks the start and leaves the tree untouched.
- Existing local-only 3DS saves are adopted and uploaded on the first start with the new app.
- Restore, upload and conflict resolution while a 3DS game runs restart the game with the new save (as for NDS); the archive is validated first and refused if invalid. The current save data is backed up as `<rom>.sav.tree-<time>.bak`. An uploaded file must be such a tar.

## Conflicts

If the server moved on in the meantime, the server never overwrites: it keeps the upload in history and opens a conflict. Decide in the app dialog or on the server page "Saves":

- use the server version, or adopt the local save ("Use Hub version" / "Adopt local save" on the server page), or
- "Keep both, decide later" (the default): the game starts with the local save and uploads for that game pause.

The app shows a per-game badge Synced / Sync pending / Conflict; the server navigation has a badge for open conflicts.

## History, restore, snapshots, slots

- Each slot has a current checkpoint ("Rev N") and a durable history ("vN"). The history can be downloaded.
- Restore a history version and create manual snapshots in the app (save history, slot picker per game) or, as an admin, in the app on a game's Saves tab with "Show saves of: All users". Saves tab › All users can also delete any history version (inline confirmation; the checkpoint and other versions stay; not the version secured by an open conflict; since `saves_v6`, before only manual snapshots) and create a slot with "+ New slot", which starts from the current version of the selected slot. A "save changed on another device" notice appears live (WSS push `save_updated`).
- Upload a save file (`saves_v4`): in the app, game page, Saves tab, "Upload save file…" (file picker: All files, Save files `*.sav *.srm *.dsv`; confirmation first; the local save is backed up, then replaced). Blocked while the slot has pending changes, like Restore; in the running game's "Manage saves" the core loads the file live (game restart), but not while that game is shared as a Session (hint shown, the server refuses with `session_running` as well). On the server's Saves page use "Upload save file" in the slot detail, the collapsible "Upload save" form on the list (user, game, slot name, default `default`, file), or the "Upload save" link on a Library row. The file becomes the slot's current checkpoint (revision + 1); the previous one goes to history as `before_upload`; a missing slot is created; identical content changes nothing; a stale expected revision is rejected (409 `save_conflict_stale`). Limit 64 MiB.
- Rename and delete slots (`saves_v5`): in the app (Saves tab › All users, admin) every slot has "Delete slot" and every slot except `default` also "Rename slot" under the slot tabs. Renaming keeps checkpoint, history and conflicts; apps pick up the new name through the `save_updated` push. Deleting asks inline, names the latest checkpoint (revision, time, device) and removes the slot with its whole history for good; it is refused when the slot changed since the view was loaded (409 `save_conflict_stale`, reload and decide again) or has an open conflict (resolve it first). The server logs every deletion. The main slot (`default`) can be deleted since `saves_v6` (the confirmation says the app starts it fresh on the next play unless it still has unsynced local progress), but not renamed (409 `save_slot_protected`). API: `POST /games/{game_id}/saves/{slot}/rename` (`{name}`) and `DELETE /games/{game_id}/saves/{slot}?confirm_revision=<Rev>`; see [reference/protocol.md](https://github.com/phabioo/uzume/blob/main/docs/reference/protocol.md).
- Rename and delete slots in the app (`saves_v5`): game page, Saves tab, under the slot tabs; "Rename slot" and "Delete slot…" appear for every slot except Main (`default`). Rename is inline (same name rules as "+ New slot"); after the server confirmed it, the local slot moves along: save folder, the core's short folder, `sync.json` and the selected slot, with unsynced local changes intact (a stale local folder of the new name is set aside as `<name>.replaced-<time>`, never overwritten). Delete asks first, shows the latest save (revision, time, device) and sends that revision as `confirm_revision`, so a slot that changed meanwhile is not deleted (the list refreshes and the message says so); it is a hard delete with no undo. The local copy is removed only after the server answered 204, and a selected slot falls back to Main. Delete is refused up front when the slot has unsynced local changes (upload or restore first) and by the server for an open conflict. A slot that exists only on this device (created with "+ New slot", never uploaded) can be renamed or deleted locally. Both actions are disabled with a hint while this game runs on this app (the server only knows shared Sessions), when the server is offline and while a Session of the game runs (`session_running`). On a `save_updated` push with reason `renamed` or `deleted` from another device the app handles the local slot the same way; if the slot is running here or has unsynced changes, the local copy is kept and a notice says so (selecting it later uploads it again as a new slot).
- Upload lock (`saves_v5`): while a Session of the same user runs a game, uploading a save file into that game's slots (app and server, `POST .../upload`) and renaming or deleting its slots return 409 `session_running`; the Saves page disables the buttons with a hint. The sync of the running game itself (`PUT .../saves/{slot}`) is not affected. The lock follows active Sessions of the user's own devices on this server; a game started without a Session is not known to the server, so the app also blocks rename and delete while its own game runs, and the upload while its own game is shared as a Session.
- In the running game, "Manage saves" restores or uploads a save as a game restart: after confirmation the local save is backed up, the game stops (saving its old state first), the chosen save is written and the game starts again; the Session stays open.
- Retention thins the history per slot: `-save-keep-recent` (20), `-save-keep-daily` (30), `-save-keep-weekly` (26); manual snapshots and versions of unresolved conflicts are never thinned. See [server-configuration.md](Server-configuration) (also editable in Settings → Network).
