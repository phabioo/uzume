How the Uzume server (`server/`, Go, SQLite) is built and behaves. Running it: [server-install.md](https://github.com/phabioo/uzume/wiki/Server-installation), [server-configuration.md](https://github.com/phabioo/uzume/wiki/Server-configuration). Rules for agents: `server/CLAUDE.md`.

## Code layout

Layout of `internal/`: `api` (generated from OpenAPI via `make generate`, oapi-codegen), `config`, `store` (SQLite, embedded SQL migrations 0001-0016, backup before migrating an existing DB), `auth` (Argon2id, tokens), `tlsutil`, `updates` (signed updates index, SemVer, selection, staging, root apply helper), `hub` (service layer for the API), `httpapi` (OpenAPI implementation incl. the WSS endpoint in `ws.go`; tests validate against `protocol/openapi/uzume.yaml`), `version`.

No web interface: since 0.18 (package 12, [ADR 0030](../adr/0030-one-app-one-server-uzume.md) D2) the server serves only the REST API (`/api/v1`, admin under `/api/v1/admin/...`), WSS signaling, file transfer, `/.well-known/uzume` and the optional `/metrics`; there are no HTML pages, cookies, templates or static assets. Administration is in the app. For the internet-facing hardening (login and pairing limits, minimum password length 12 via `hub.MinPasswordLen`, read deadlines, 512 connection cap, TURN relay limits) see [server-configuration.md](https://github.com/phabioo/uzume/wiki/Server-configuration#turn-security).

## Saves and Sessions

- Saves are stored as files under `<data dir>/saves/`, SQLite holds metadata only; a stale base creates a conflict and never overwrites ([ADR 0005](../adr/0005-saves-phase3.md)).
- Sessions: session API plus WSS presence and signaling relay; the server never touches media (audio/video flow directly between apps) ([ADR 0006](../adr/0006-sessions-phase4.md)).
- An owner device that disconnects has a 30 s grace period before its Session ends.

## Users, invites and uploads

- Server › People › Invites (admins, admin API): create onboarding invites (code `FB-XXXX-XXXX`, single use, expiry 15 min / 1 h / 24 h, optionally authorizing the first device directly). The code is shown once; only a hash is stored. The app redeems it with `POST /api/v1/invites/redeem` (rate limited), which creates a passwordless user and either a trusted device (200) or a pending request pre-assigned to that user (202; the admin allows it under Server › People › Devices, "Assign user" defaults to the invite user).
- Admins can delete users and devices for good through the admin API (the app asks "Confirm it's you"): deleting a user removes their devices, invites, saves and save history; uploaded games are reassigned to the deleting admin. The handshake response carries the optional `user` (id, display name, role) of the caller (API 1.7.0).
- Admins can disable and enable users. A disabled user gets `401 user_disabled` on every bearer call and the token exchange, their WSS connections are closed and their Sessions end; saves and uploads stay. 
- Settings: "Allow users to upload games" (default off) lets users call `POST /api/v1/games` (raw body, streamed to disk, max 4 GiB, same hashing and de-duplication as the admin upload; `uploaded_by` is the caller).
- Accounts (0.18 package 4, feature `accounts_v1`, migration `0020_accounts.sql`, `internal/hub/accounts.go`, `internal/httpapi/accounts.go`): `devices` gets `sign_in_kind` (`approval`, `invite`, `password`, `local`), `install_id` (shared by the users of one app install on one PC, one device row per user), `confirmed_until` and the confirmation lock (`confirm_failures`, `confirm_failed_at`, `confirm_locked_until`); `users` gets `password_changed_at`, `must_change_password` and the sign-in lockout (`sign_in_failures`, `sign_in_failed_at`, `sign_in_locked_until`); `pairing_requests` gets `sign_in_kind` and `install_id`. Every user may have a password (Argon2id like the admin's; at least 12 characters), admins must; the policy `require_passwords` only blocks removing a password and touches no existing user. Sign-in is per user name and per IP (10 attempts a minute; 15 min lock after 10 failures, unknown names included). "Confirm it's you" is valid 120, 300 or 900 s per user and device; 3 wrong passwords lock it 5 min on that device. The hub helper `RequireConfirmed` guards dangerous admin steps (backup restore and delete, update rollback, password reset, accounts settings) and is meant for the admin API of package 5 too. An admin reset sets a temporary password and `must_change_password`. Demoting an admin keeps the password. The web admin and its cookie login were removed in package 12. The PIN for user switching is app-side only and never reaches the server.

## Systems, cores and firmware

- Cores from the libretro buildbot (0.8, [ADR 0020](../adr/0020-cores-from-the-libretro-buildbot.md); `internal/hub/{cores,corecatalog,coreinstall,coreimport}.go`): migration `0009_core_catalog.sql` adds `systems.libretro_ids` and `systems.default_core_id`, the table `system_cores` (installed core per system: version, origin, display name, license, `required_hw_api`, `build_date`, `crc32`, upstream info) and `profiled_cores` (cores with an app profile: `melondsds`, `desmume`; all others are experimental). Package rows (`core_packages`, `core_package_files`) are unchanged; packages of the retired signed source (origin `legacy-mirror`, e.g. `melonds_ds`) are removed at start (`removeLegacyCores`, rows and files; migration `0011_provisioning_text.sql` replaces the old provisioning text "Included in the Player"); `melonds_ds` stays an alias of `melondsds` in the handshake core check, which accepts any core the server serves for the system. The catalog (info.zip, `.index-extended` per served platform `windows-x64`/`linux-x64`) is refreshed at start, every 24 h and by "Check source now"; install pins the SHA-256, versions are `YYYY.MM.DD[.N]`; installs are admin actions; installed cores are updated automatically after each successful refresh when the setting `core_auto_update` (default on) is set, with the same safeguards as a manual Update (SHA-256 pinned, old build removed only after the new one is cached; a failing core does not stop the others, last error shown on Systems & Cores). `import-cores` reads `<dir>/<platform>/<core>_libretro.<suffix>.zip` plus optional `info.zip` and `.index-extended`. `-core-trust-key` only applies to the updates index; `-core-index-url` is ignored.
- Systems are data-driven (`internal/hub/systems/<id>.json`, embedded; `systemdefs.go`): at start (`hub.Open`, after the migrations) `reconcileSystems` inserts missing systems (firmware mode `builtin`, no default core), updates only the definition columns (name, extensions, libretro ids, platforms, provisioning, profiles) and firmware definitions of existing ones, replaces `profiled_cores` from the files, and never touches admin state or systems without a file. A catalog core is offered, installable and importable for a system when its `systemid` is in `libretro_ids` and its `supported_extensions` is empty or shares an extension with the system. Systems: `nds`, `3ds`, `gb`, `gbc`, `gba`; a test checks them against the app manifests in `client/emulation/manifests/`.
- Server › Systems & cores: registry (default core via the Cores tab), the last handshake report per device (core/version status; a missing or other core only warns, `compatible` stays true) and the firmware path.
- Firmware mode per system: `builtin` (core uses its own firmware, files optional) or `native` (files required). The admin provides files (size is validated; an optional admin-pinned SHA-256 must match) under `<data dir>/firmware/<system>/<file_id>` (mode 0600). Server never ships or invents BIOS/firmware or hashes; contents are never logged and only leave the server through `GET /api/v1/systems/{system_id}/firmware/{file_id}` (ETag = SHA-256). The nav badge "N firmware" counts required files that are missing or mismatching.

## Updates

The server checks a signed update feed and can install new versions of itself when it runs from the `.deb` package. The spec is `docs/roadmap.md` (0.3 "Automatic updates") and [ADR 0011](../adr/0011-automatic-updates.md); package and units are under `packaging/linux/`. User-facing description: [updates.md](https://github.com/phabioo/uzume/wiki/Updates).

- Version info: `uzume-server version [--json]` prints one JSON object `{"product":"hub","version","channel","commit","protocol_version","min_protocol_version"}`. Build with `-ldflags "-X .../internal/version.Version=<v> -X .../internal/version.Channel=<stable|beta|dev> -X .../internal/version.Commit=<sha>"` (defaults `dev`, `dev`, empty). Versions are SemVer 2.0 and compared by precedence (build metadata ignored); a non-SemVer version such as `dev` disables the updater.
- Feed: the release tag `updates-index` holds `updates-index.json` and `updates-index.json.sig` (Ed25519 over the exact bytes, same signature format as the retired core index, [ADR 0010](../adr/0010-cores-from-the-hub.md), [ADR 0011](../adr/0011-automatic-updates.md)). `-update-index-url`/`UZUME_SERVER_UPDATE_INDEX_URL` overrides the URL (https, or `file://` for tests; `file://` artifact URLs are accepted only when the index itself came from `file://`). Extra trusted keys: `-core-trust-key`/`UZUME_SERVER_CORE_TRUST_KEYS`, which now cover cores and updates. Unknown schema or duplicate (product, channel, version) rejects the index; invalid releases are skipped.
- Server › Settings › Updates (admins, in the app): channel (`stable`, `beta`; `dev` builds default to off until a channel is selected; `beta` also sees stable releases, the highest SemVer wins; never a downgrade), automatic install (default on for beta, off for stable), "Check now", "Install update" (with confirmation). Checks run in the background at startup, hourly on beta and daily otherwise, and never block or fail startup. Settings live in the `settings` table (`update_channel`, `update_auto`, ...). Release builds are compiled `beta`; with no `update_channel` set, the first successful index load stores `update_channel_default` (`stable` if the index lists the running version as stable, else `beta`; never re-resolved; an explicit `update_channel` wins; [ADR 0016](../adr/0016-release-numbering-and-promotion.md)).
- Protocol: a candidate whose `min_protocol_version` is above the protocol version of any app seen in the last 30 days (`device_reports`) is "breaking": the app (Server › Overview or Server › Settings › Updates) warns, automatic install skips it, a manual install asks for a second confirmation.
- Install path: the server (service user) downloads the `.deb` for `linux-<GOARCH>`, verifies size and SHA-256 against the signed index, writes it with the exact index and signature to `<data dir>/updates/staged/` plus `staged.json`, and creates `<request dir>/update-request` (`-update-request-dir`/`UZUME_SERVER_UPDATE_REQUEST_DIR`, default `/run/uzume`). Automatic install does not run during an active Session and does not retry a version whose last attempt failed. This needs a packaged install (executable `/usr/bin/uzume-server`, writable request dir); otherwise the app shows the version, the download link and the manual command.
- Root helper `uzume-server update apply-staged` (run by `uzume-server-update.service` as root; reads `UZUME_DATA_DIR` and `UZUME_SERVER_CORE_TRUST_KEYS`): deletes the request file first, re-verifies the staged index signature with the compiled-in and env keys only, requires a version strictly newer than its own (no replay of old signed releases), requires the `linux-<arch>` `deb` artifact named in `staged.json`, never follows symlinks in the data directory, copies the package into a root-owned private temp directory, verifies size and SHA-256 of the copy and runs `dpkg -i` on it. The result goes to `<data dir>/updates/last-result.json` (owned like the data directory, shown on the Settings page).
- CLI: `uzume-server update check [-channel stable|beta]` prints the selection as JSON (`current`, `channel`, `platform`, `up_to_date`, `available` with artifact, `skipped`); `uzume-server update stage [-channel ...]` additionally downloads, verifies and stages the update and creates the request file (run as the service user). Without `-channel` the server's stored setting applies (if the database exists), else the build channel; a `dev` build needs `-channel`. Both accept the usual config flags (`-data-dir`, `-update-index-url`, `-core-trust-key`, `-update-request-dir`).
- Save comfort (ADR 0012 D7, feature `saves_v2`): history retention per slot `-save-keep-recent` (20), `-save-keep-daily` (30), `-save-keep-weekly` (26) (`UZUME_SAVE_KEEP_*`, 0 = unlimited for that rule; manual snapshots and versions of unresolved conflicts are never thinned), run after each history insert and as a daily sweep (also at start); restore and manual snapshot endpoints and a `Restore` / `Create snapshot` action under Saves tab › All users (admin changes are recorded with the nil device id; older entries read "Hub web interface"); `save_updated` WSS push to the user's other connected devices. The last verified core index (`<data dir>/cores/index.json` + `.sig`) is served as `GET /api/v1/cores/index` and `/index.sig` (feature `cores_index_v1`, 404 until a sync or import has verified one).
- Server saves (0.7.x, feature `saves_v3`, migration 0007 adds `save_slots.history_high` so history version numbers are never reused after a delete; feature `saves_v4`, migration 0008 `0008_save_upload.sql` widens the reason CHECK constraints for `upload` / `before_upload`): `DeleteSaveSnapshot` removes a `manual_snapshot` history version (checkpoint untouched; the content file is dropped once nothing references it); `CreateSaveSlot` (admin API) copies the selected slot's current version into a new slot as revision 1 (reason `restore`) plus history v1 as a manual snapshot.
- Rename and delete save slots (0.10.x, feature `saves_v5`, no migration): `Service.RenameSaveSlot` renames `save_slots`, `save_history` and `save_conflicts` rows in one transaction and moves the slot directory (`saves/<user>/<game>/<slot>`) before the commit (moved back if the commit fails). `Service.DeleteSaveSlot` is a hard delete in one transaction (conflicts, history, slot) followed by removing the directory; it needs `ConfirmRevision` = current revision (`ErrSaveConflictStale` otherwise), refuses open conflicts and logs via `slog`. Both refuse the `default` slot (`ErrSaveSlotProtected`) and a running Session (`ErrSessionRunning`: `sessions` row of the slot owner with the same `game_id` and `ended_at IS NULL`, checked under `saveMu`); `UploadSaveFile` checks the same lock before staging and again inside the transaction. Push: `save_updated` with reason `renamed` (+ `previous_slot`) or `deleted`.
- Database backup: before schema migrations are applied to an existing database, `VACUUM INTO <data dir>/backups/hub-<from>-to-<to>-<UTC yyyymmddThhmmssZ>.db` is written and the newest 5 are kept; a failed backup aborts startup with a clear error. Fresh databases are not backed up.
- Index maintenance (`uzume-sign`): `release-add -index <updates-index.json> -release <release.json> [-keep 5]` adds or replaces one release (creates the index if missing), keeps the newest `-keep` per (product, channel) by SemVer, sets `generated_at` and writes sorted, deterministic JSON; `sign -index <file>` detects an updates index (object with `releases`) versus a core index (`packages`); `verify` stays byte-level.
- Rollback ([ADR 0029](../adr/0029-operations-and-safety.md) D4, [guide](https://github.com/phabioo/uzume/wiki/Updates#rollback)): `uzume-server rollback`, admin API `/api/v1/admin/updates/{versions,rollback,resume}` and Settings → Updates → "Earlier versions". The server keeps `update_history` (versions it ran), and while paused `update_paused`, `update_skip` and `update_auto=0` in `settings`. The helper restores the pre-update backup only with a confirmation (`Staged.RestoreDB`, `settings.json` in the staged directory). The manual `apt install --allow-downgrades` stays the fallback.
