# ADR 0029: Operations and safety

- Status: Accepted for D1 to D5; further decisions (Hub health) follow in later 0.17 PRs
- Date: 2026-10-22
- Deciders: Fabio

## Context

Roadmap 0.17 ([roadmap.md](../roadmap.md)) collects the operations items that matter before a test evening. The Hub so far installs as a Debian package or with `install-hub.sh` on a systemd host and updates itself through a root helper ([ADR 0011](0011-automatic-updates.md)). Many self-hosters run everything in Docker (NAS, home server) and expect an image.

## Decisions

### D1 Docker image for the Hub

- **Registry and tags.** `ghcr.io/<owner>/framebeam-hub` (GitHub Container Registry, same repository and `GITHUB_TOKEN` as the releases; no extra account or secret). Tags: `X.Y.Z` for every beta and release, `beta` for the newest `main` build, `stable` and `latest` for the promoted release. `release.yml` pushes `X.Y.Z` and `beta` from the binaries CI built and tested (Dockerfile target `hub-prebuilt`, no rebuild, same number as the `.deb`). `promote.yml` adds `stable` and `latest` to the existing manifest with `docker buildx imagetools create`, also without a rebuild. CI builds the image for `linux/amd64` and `linux/arm64` and starts the amd64 one on every change, but never pushes.
- **Image.** `packaging/docker/Dockerfile`, multi-stage. The Go stage runs on the build host and cross-compiles with `CGO_ENABLED=0` (pure-Go SQLite), so arm64 needs no emulation. The runtime is `gcr.io/distroless/static` (no shell, no package manager, CA certificates included). Version, channel and commit are baked in with the same ldflags as `make build-hub`.
- **Volumes.** One volume `/data` (`FRAMEBEAM_DATA_DIR`) holds all state: database, saves, firmware, ROM library, certificate, cores, plugins, backups. Backup is a copy of that volume. Nothing else in the container is state.
- **Non-root.** The container runs as uid/gid `65532`. The `/data` directory in the image is owned by that user so new named volumes work; bind mounts need a `chown`.
- **Ports.** Web `8443/tcp`; with the embedded TURN relay `3478/udp+tcp` and the relay range (default `49160-49199/udp`). The user publishes what the configuration needs.
- **No self-update in the container.** The image sets `FRAMEBEAM_HUB_CONTAINER=1`. The updater's package check (`updates.IsPackaged`) then returns false, so the Hub still checks the index and shows "Update available", but never stages or installs a `.deb`; Settings shows how to update (pull the new image and recreate the container). Automatic install is off for the same reason. There is no root helper or systemd path unit in the image to begin with.
- **No `HEALTHCHECK`** for now: the image has no shell or curl and the Hub has no health command. The Hub health page (later in 0.17) can add one.

### D2 Backup and restore

- **One archive.** A plain `.tar`, `framebeam-hub-<hubname>-<UTC timestamp>[-safety].tar`, written to a folder the admin chooses (default unset, which means backups are off). Members: a `VACUUM INTO` snapshot of the database (the Hub keeps running), the `saves/` (with history and snapshots), `states/` (if present), `plugins/`, `firmware/` and `tls/` trees, files outside the data folder (own TLS certificate and key, `hub.env`) under `config/`, the ROM library only with "Include ROMs", and `manifest.json` as the last member with the Hub version, the database schema version, the contents and the SHA-256 of every file. Cores (re-downloadable, ADR 0020), logs and temporary files are not included. The manifest is last so every file is hashed while it is written (one pass, no second copy of 40 GB of ROMs); listing a folder reads only the tar headers. The archive holds secrets (TLS key, hashes); the guide says so.
- **Write safely.** The archive is written to a hidden `.partial` file in the target folder and renamed when complete; cancel and every error remove it. Free space is checked first (payload plus overhead); too little space fails with "Not enough space on <folder>: needs X, Y free". Decision 26: the Hub never deletes a backup to make room.
- **Retention.** "Keep last N" (default 7) removes the oldest regular backups after a new one succeeded. A failed backup removes nothing. Safety backups are never pruned.
- **Schedule.** Off, daily or weekly (+ weekday) at a local time, kept in the settings table and run by a scheduler in the Hub process (it re-reads the settings every 5 minutes so the CLI can change them). Days are calendar days, so daylight saving time does not move the run. A run missed while the Hub was down is not made up. One backup or restore at a time; a backup can be canceled; progress (phase, bytes done and total) is exposed for the status card and the API. The save lock is held only for the snapshot and the file listing; a file that vanishes later (history sweep) is skipped and counted.
- **Restore.** Always preceded by a safety backup. The chosen archive is verified file by file against the manifest while it is unpacked into `restore-staging/` inside the data folder (same file system, so the swap is a rename); a damaged archive or one from a newer database schema than the running Hub stops before anything changes. The swap itself runs at the start of the Hub process, before the database is opened: a `restore-pending.json` marker names the staged items, each live item is moved to `restore-old/`, the staged item is renamed into place, and a `COMMITTED` tag ends the swap. Failure rolls everything back; a crash is repaired at the next start (roll back and retry, or only clean up when committed). The result (`restore-result.json`) feeds the "Restored" and "Not restored" cards. `framebeam-hub restore` does the same with the Hub stopped, guarded by an exclusive lock on `hub.lock` that the serving Hub holds (a second Hub on the same data folder is refused too); run as root it gives the files the owner of the data folder.
- **Restart.** The Hub restarts itself with the existing mechanism (graceful shutdown, then `exec` of the same binary on Unix, an in-process restart on Windows), so no `Restart=` or Docker restart policy is needed; `Restart=on-failure` stays as the safety net.
- **Interfaces.** The CLI (`backup`, `backup list|config|verify`, `restore`) and the admin REST API `/api/v1/admin/backups` (OpenAPI 1.24.0) are the primary interfaces; Settings → Backups is a plain page on the same service functions. The Status page gets a "Disk · backup" card and the problems "Backup failed" and "Cannot write" (both amber, shown in the banner and the sidebar badge).

### D3 Problem reports

- **Destination.** A Player sends a report only to the Hub it is connected to (its own Hub), never to a third party; the Hub never forwards it. Reports are kept until an admin deletes them.
- **API first.** `POST /api/v1/reports` (any paired device, handshake feature `reports_v1`, `multipart/form-data`: JSON part `meta`, then files) and admin endpoints for list, get, file, zip archive, seen and delete. The Hub web page is a plain view of it, because admin moves into the Player app.
- **Content.** A short description plus attachments chosen in the Player: logs of the last 3 days, redacted settings, an optional connection check, optional system info. Never passwords, the Hub pairing token, ROMs or saves. The Player redacts before sending; the Hub redacts text attachments again (shared package `internal/redact`, also used by the diagnostics bundle).
- **Limits.** 25 MB and 12 files per report, 8000 characters of text, 5 reports per device and hour. File names are reduced to their base name; the Hub logs only id and device.
- **Storage.** Tables `reports` and `report_files` (migration 0019), files under `<data>/reports/<id>/`, written in a staging directory and renamed, so a crash leaves no half report.
- **Status.** New reports raise only the ADMIN → Reports nav badge ("n new"), not a Status problem. Opening does not mark seen; "Mark as seen" does.
- **Offline.** If the Hub is unreachable the Player keeps the dialog, retries once the connection is back, and offers "Save as file…" with the same zip.

### D4 Update rollback

Finishes [ADR 0011](0011-automatic-updates.md) D8. Single-plugin rollback is not part of it (decision 32); runs keep their pinned plugin version.

- **Candidates.** Releases of the same product and platform from the signed index (verified and fresh like for an update): the channel of the install (beta also sees stable) plus the versions the device actually ran, from a small local history (`update_history` in the Hub's `settings` table and in `player.json`, first and last day, capped at 20 entries). Strictly older than the running version, never older than the oldest version that speaks the current `protocol_version`, newest first, at most 5 (the Player screen draws 3). A version listed in two channels counts once, stable wins.
- **Hub schema.** Migrations stay forward-only. The index entry carries `schema_version` (from `framebeam-hub version --json`); an entry without it is unknown. A target that knows the current schema keeps the data. A target that needs an older schema may only restore the automatic pre-update backup of exactly that step (ADR 0011 D6, `hub-<from>-to-<to>-*.db`); the confirmation names what is lost ("changes since <time> are lost; kept in the safety backup") and must be given explicitly. Without such a backup, or with an unknown schema, the rollback is refused with the reason. Before anything changes the Hub writes a safety backup without ROMs with the D2 code (backup folder, else `<data>/backups`).
- **Root helper.** The rollback reuses the update path: `Stage` writes the same staged directory (plus the optional `restore_db` name and `settings.json`), and `update apply-staged` re-verifies everything and trusts nothing in the data folder: signature and freshness of the stored index, strictly older, protocol, the database backup name and the schema it was taken with. A database restore stops the service, moves the live database aside, puts the backup in place (with the update state written into it, see below), installs the package and starts the service; a failing installer puts everything back. On Windows the same runs in `update watch`. A container is never rolled back by itself (`FRAMEBEAM_HUB_CONTAINER`): the page and the CLI print the older image tag to pull.
- **Pause and skip.** After going back, automatic updates are paused until "Resume updates", and the version that was left is "skipped · available": never installed automatically, "Update to X" installs it. The state lives in the data the older program reads (Hub `settings`: `update_auto=0`, `update_paused`, `update_skip`; Player `player.json`: `update_auto_install=false`, `update_paused`, `update_skip`), so an older binary that knows nothing of this feature stays quiet too, and a restored database carries it (the helper writes the keys into it). The pause holds while the running version is older than the one left; it ends by itself when the running version reaches it, or when the helper reported a failure or nothing happened within 30 minutes (Hub). Resume restores the previous automatic-install setting.
- **Player.** The installer is downloaded from the index, verified (signature of the stored index, freshness, strictly older, protocol, size, SHA-256) and started through the update launcher copy, which checks size and hash again. Never while a game or Session runs. The MSI is authored with `MajorUpgrade AllowDowngrades="yes"` so a downgrade keeps the data; an MSI built without it refuses to install over a newer version, so releases built with it set `msi_downgrade` in the index (from `--version-json`) and only those are offered. Settings stay (unknown keys are preserved). A plugin manifest may declare `min_player`; a plugin that needs a newer Player has the problem "Needs Player X", is not started and turns on again after the update. Portable, Linux and development builds list the releases with links only.
- **Interfaces.** `framebeam-hub rollback --list [--json] | <version> [--yes] [--confirm-data-loss] | --resume`; admin API `GET /api/v1/admin/updates/versions`, `POST /api/v1/admin/updates/rollback`, `POST /api/v1/admin/updates/resume` (OpenAPI 1.26.0); Settings → Updates in the Hub web is a plain page on the same service functions (the admin moves into the Player app in the next milestone). Status page and API show the problem "Updates paused" (info, amber) while paused.

### D5 Connection check in the Player

- The Player's connection check is its own set of probes (Hub info endpoint with the pinned certificate, STUN binding from one socket to at least two destinations, TURN allocate with the Hub's short-lived credentials and an immediate refresh to free it) plus a WebRTC loopback inside the Player. NAT type comes from comparing the mapped addresses of two destinations for the same socket: equal means endpoint-independent, different means symmetric, and one answer means undetermined.
- The check claims "direct possible" only as an estimate and says so. It proves the relay path end to end only when the relay is needed. The result is exported as plain text and as JSON (`connection-check.json`). Neither contains relay credentials; both contain addresses and server names.
- "Add to problem report" attaches the result to the next "Collect logs" bundle once and marks it for the "Report a problem" dialog (D3), which lists the last result as an attachment and starts it checked when marked. A Player without an open Hub session stops after step 1, because the Hub's ICE servers are unknown.
- Deviations from 6e: two extra outcomes ("Connections to other networks are not possible from here", "Connect to <Hub> to run the full check"), no "about 30 ms more", NAT labels "Open · endpoint-independent" / "Symmetric NAT" / "Not determined"; entry points Settings → Hubs and Diagnostics.

## Rejected

- **Docker Hub as registry:** needs an account, a secret and pull rate limits; GHCR is already where the project lives.
- **Rebuilding the image in `release.yml` or `promote.yml`:** the stable image must be exactly the tested beta (ADR 0011); `imagetools create` re-tags the manifest.
- **Alpine or Debian runtime:** a shell and a package manager add attack surface and size; the Hub is one static binary.
- **Backup by copying the data folder with the Hub running:** the SQLite file and its WAL are not consistent that way; hence `VACUUM INTO`.
- **Compressing (tar.zst/gz):** saves and ROMs hardly compress, and it would add a dependency or a CPU load on a Raspberry Pi; the format can get a compressed variant later.
- **Pruning to make room on a full disk:** decision 26; the Hub only warns.
- **Rolling back to an MSI that was built without `AllowDowngrades`:** Windows Installer would refuse it; the list only offers releases that say they can (`msi_downgrade`), the rest stays a manual install.
- **Guessing the schema of a release that does not say it:** the rollback is refused; replacing a database on a guess could lose data.
- **Starting the older version first and pausing afterwards:** the older program could update itself back before the pause exists; the state is written before the installer starts (and reverted when nothing started).
- **Letting the container update itself** (for example by replacing the binary in the writable layer or in `/data`): the change would be lost on the next recreate and bypasses the image as the unit of upgrade and rollback.

## Consequences

- Fabio must set the GHCR package `framebeam-hub` to public after the first push (package settings), otherwise `docker pull` needs a login.
- Docker users update with `docker compose pull && docker compose up -d`; the Hub keeps its database copy in `/data/backups` before a schema migration.
- The guides are [server-docker.md](https://github.com/phabioo/uzume/wiki/Server-in-Docker) and [server-backup.md](https://github.com/phabioo/uzume/wiki/Server-backup).
- The Hub now holds `hub.lock` in the data folder while it runs; a second Hub on the same folder refuses to start.
