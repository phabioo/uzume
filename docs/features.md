Look and input (readable UI pass, [readable-pass.md](design/uzume/readable-pass.md)): yellow marks only the main action, focus and the active nav item; warnings are a sentence with a yellow square. Settings › This PC › Appearance has Text size (100 %, 125 %, TV; setting `text_size`) and Reduce motion (`reduce_motion`). Every main page has one page header and at most three columns below 1440 px (help and the controller input test fold into disclosures); dialog buttons stack when they do not fit. Keyboard and gamepad reach every page: section columns, binding fields, the screenshot strip and the Continue tile are focusable, B / Esc goes one level back, and outside a running game the pad's D-pad / stick, A, B, Y and L / R drive the interface, with a hint row after pad input.

Settings (usability pass): one place for everything set on this PC, one page per section under the heads You (Account, Appearance), Playing (Picture & sound, Controls, Hotkeys, Emulation) and This PC (Folders & storage, Servers, Plugins, Updates, Help & diagnostics). No scope toggle: it covers this PC and your account only; Servers has a "Server settings" link for admins. Emulation has a tab per system, Controls a tab per device; the sidebar's PLAY group is Library and Runs, Ctrl+3 / Ctrl+4 open Emulation and Controls.

There is no web admin: the server serves only the REST API (`/api/v1`, admin under `/api/v1/admin/...`, feature `admin_v1`), WSS signaling and file transfer, and no HTML pages. Administration is in the app (sidebar item "Server", admins only).

## Library and ROMs

- Library with one toolbar: search (Ctrl+F), chips All and Favourites with counts and a "Systems…" menu (systems, collections and status Ready / Needs attention / Not downloaded; one scope at a time; pad L / R steps through the status), sort (with "Ready first" in its menu), a List / Grid switch (setting `library_view`; grid tiles with monogram and system chip), folder counts. A row, tile or Enter opens the game page (full width; "‹ Library", Esc or pad B return with selection and scroll kept): header with Favourite, Start a run…, Play and a ⋯ menu (Add to collection, Play and share), tabs Overview (problem box, "Continue from" slots, "How it plays" with Change links), Saves, Settings (the per-game settings) and Manage (file details, local file actions, admin Rename and Delete; saves are kept). The game page shows the primary action in the header and at most one problem sentence; when it blocks play, its fix is the primary ("Install core and play", "Open Systems & cores" for admins, "Ask an admin"). The start checklist shows only while starting or after a failure; the Saves tab has Play from Main and Start a run on top and File details closed. Removing a local game shows a toast with Undo; the file stays on the PC.
- ROM upload from the app (resumable); the setting "Members can add games" (Server › Games) controls whether non-admins may upload. ROM download via API with Range and ETag.
- Hash-verified ROM cache with resumable download; limit in Settings (`rom_cache_limit_bytes`, default 20 GB, 0 = unlimited), LRU by last use, "Clear ROM cache" with confirmation.
- Storage overview (Settings › Folders & storage): measured in the background (path, time, Measure again), one bar with Downloaded games, Save cache, Save states, Screenshots waiting for upload, Cores and firmware and the free space of the volume; clean-up suggestions with sizes and a confirmation each: games not played in 60 days (they download again when you play; never the running game or a download in progress) and older cached core versions not in use. Clean-up never offers saves.
- Local ROMs ([guide](guides/local-roms.md), [ADR 0025](adr/0025-local-roms.md)): Settings › Folders & storage; the app scans, hashes (cache by path + size + mtime) and registers ROMs, starts them straight from the folder and shows "Local" / "Missing". Games merge by identity (system, game code, version), several files per game, saves stay on one game. Local-only games are visible to their owners (admins see all); optional resumable upload (64 MiB chunks). Feature `local_roms_v1`; no P2P.
- Above the Library table: one notices line (the most important notice, "+N more" expands the rest, one action link) instead of separate banners, and a Continue row of up to three compact cards (same start path as Play), hidden until a game was played on this PC.
- Play time, favourites and collections (per user, on the server): the server counts play time from the app's presence (`in_game` with game, and run for run games; a play closes on state, game or run change, disconnect, replaced connection or shutdown; dangling plays are closed at the last heartbeat on start; plays under 10 s are dropped). Per game: play time, sessions, last played, favourite flag and collections; per user and run (per participant and total): play time and last played. Collections are named lists (1 to 40 characters, unique per user ignoring case); deleting one never deletes games. Removing a game removes its favourites and collection entries; play time stays in the user and run totals. Library: filter chips All / Favourites / collections / "+ Collection", sort by Recently played, Name or Play time, played and last played columns; "last played" is the newer of the server and local value.
- Save states, run rules and cheat marker (server side and, since 0.20 package 4, the app: slots A and 1 to 4 per game and save slot, F6 save / Shift+F6 next slot / F8 load, Auto kept before a load with Undo, rewind (hold Backspace) and run-ahead, sync with `states_v1` and offline cache; details in `docs/guides/app.md`): the server stores per user, game, save slot and number (0 = quick slot, 1 to 10) one state of up to 64 MiB with a preview PNG, the core id and version and the device; a state in the same place is replaced. Each person has a quota (default 2 GiB, Server › Settings via `state_quota_bytes`); past it the upload is refused. States are part of backups, go with a removed user and stay when a game is deleted until the Storage clean-up "States of deleted games" removes them. Runs carry core rules (save states, rewind, cheats and memory changes off or logged; all off by default) that only the creator or an admin changes, at any time; the change is logged as `rules.changed` and pushed live. Saves can be marked "cheats used" by the app, history versions keep the marker, and snapshot labels may be up to 120 characters.
- Run rules and cheat database setting (app, 0.20): "Start a run" has a compact "Game rules" block (save states, rewind, cheats and memory changes off or allowed and logged) that is sent with the run; the run view shows the rules in one line, and the person who started the run or an admin opens "Rules…" to change them at any time (others see them read-only). A change updates every open run view live, appears in the run log and, in a running game, raises the toast "<name> allowed cheats in this run". The Server settings page "Cheat database" (admin, with "Confirm it's you") shows source, status and age with "Refresh now", and Settings › This PC shows the same for an own "Only on this PC" server, else a read-only line. A permission that changes the game (`cheats`, `memory.write`) carries a "Changes the game" tag and a short note in the plugin list, detail and server offer. The cheats question of a remembered game is asked at the first action in the game, not at game start.
- Save history and cheats (app, 0.20, design 11g): a history version the server marks `cheats_used` shows a "Cheats" tag and "made with cheats"; the safety copies "Before cheats" and "Before memory changes" that the app takes before the first cheat or memory write are automatic entries with their own tag and the text "Automatic · made before …", have no Delete, and offer "Restore before cheats" (or "Restore before changes") as the one primary action; the confirmation says that cheats you turned on stay on. The slot tabs stay fully visible above the "Delete slot…" row after the view got shorter.
- Plugin store and cheat database (server side, 0.20; the app and the cheats plugin follow): every person has a small key/value store per plugin that follows them to every PC (values are JSON of up to 256 KiB, up to 16 MiB and 1024 keys per plugin). A write names the revision it is based on; a stale write is refused with the server's value, so the app can keep both versions. Nobody else reads a value, not even an admin; the store is part of backups and goes with a removed user. The server also keeps a cheat database: it downloads the cheat lists of the libretro-database and the No-Intro DATs in the background (or imports them offline), matches a game by its ROM hash to the No-Intro name and its list (3DS games by title ID from Gateway lists, since libretro-database has none, else by file name) and serves the cheats of a game with a guess of the code format. The database is not part of backups (it is downloaded again). The admin sees age, size and the last result and can change the source or refresh now (Server settings follow in the app); setup in [server-configuration.md](guides/server-configuration.md#cheat-database).
- Screenshots (per user, on the server): F12 or Select + Y in the game (also "Take screenshot" in the game's ⋯ menu) captures the native frame as PNG; the app keeps it in `<data>/screenshots/pending/` until the server accepts it (retry on the next connection; a refused picture is dropped with a log line). The server stores PNGs up to 16 MiB per user and game, optionally tagged with a run (run members see a run's screenshots), and counts their size per user and game; screenshots are part of backups, go with a removed user or game and stay when a run is deleted. Game page: "Screenshots (N)" strip with dates and a viewer (Previous / Next, Save as..., Delete...).
- Background game: "← Library" pauses the running game and keeps it loaded (a shared Session stays shared); the Library shows "Now running" with Resume and Quit game, and starting another game asks first. Known slow: Library loading with many (500+) games.

## Saves

- Versioned saves per user and game (API tag `saves`, feature `saves_v1`); the server stores the save as an opaque blob, never merges it and never sends it to another server. Details: [guides/saves.md](guides/saves.md).
- Sync with the server: sync before launch, auto checkpoint while playing (12 s after the last change, at most every 60 s), final sync on pause, stop and exit; pending uploads are kept per server and user.
- Conflict dialog with "Keep both, decide later" as default; per-game badge Synced / Sync pending / Conflict.
- Slots per game (slot picker), history with Restore, manual snapshots, retention/thinning (`-save-keep-recent|daily|weekly`), `save_updated` push over WSS, live "save changed on another device" notice. Feature `saves_v3`.
- Upload a save file into a slot (`saves_v4`) from the app or API: the file becomes the current checkpoint and the previous one goes to history as `before_upload`; the local save is backed up first. Blocked while the game runs or the slot has pending changes.
- Rename slot and delete slot for every slot except Main (`saves_v5`); with `saves_v6` also the main slot and any history version can be deleted on the server. Delete is a hard delete and asks with the latest save. Rename and delete are blocked while the game runs on this app; save upload is blocked while a Session of that game runs.
- "Manage saves" in the running game's panel shows slots and history live (snapshot, delete, restore, upload) and resolves conflicts inline; restore and upload apply as a game restart.
- the Saves tab of a game, "Show saves of: All users" (admin): saves of all users, slots, conflicts ("Use Hub version" / "Adopt local save"), history with Download, restore, snapshot, delete a snapshot, create a slot; badge in the navigation.
- CLI: `saves list`, `save push`, `save pull`, `save resolve`.

## Sessions and Multiview

- Share a running game as a Session with visibility "Private" / "Hub users" / "Invite only", invites, Join/Decline and viewers; "Sessions on this Hub" in the library. The server provides the session API, WSS presence and signaling relay, and revokes on visibility change.
- Watch a Session over direct WebRTC (H.264 + Opus); watch-only mode without a running game. CLI: `session-share --synthetic`, `session-watch`.
- Multiview: up to 4 surfaces (local game plus up to 3 remote Sessions, or 4 remote Sessions) as Row (2-3 Sessions), Grid 2 x 2 (from 4) or PiP (PiP inside the main tile; docked diagnostics, floating only in fullscreen); exactly one audible surface ("Audio here") unless "Mix all tiles" is on (Mixer popover, 0.23); the picker lists all Sessions; viewers see "Paused by <name>" on a frozen tile. Encoding runs on a worker thread; under load the oldest pending video frame is dropped. Design: [ADR 0026](adr/0026-ui-gaps-and-multiview.md).
- ICE: a public default STUN server (`stun:stun.cloudflare.com:3478`) when none is configured, switched off with `-ice-servers none` / `UZUME_ICE_SERVERS` or "Use no external server" in Server › Settings › Network & sharing; running apps pick up ICE changes via `ice_update_v1`.
- Sessions over the internet ([ADR 0012](adr/0012-internet-sessions-and-save-comfort.md), [guide](guides/sessions-over-the-internet.md)): optional embedded STUN/TURN relay (`-turn`, `-public-host`; off by default) with short-lived credentials, Cloudflare TURN (API token as a secret on the server host), or any external TURN server such as coturn on a VPS with a shared secret or static login, set in Server › Settings › Network & sharing or via `-turn-external` ([coturn-on-a-vps.md](guides/coturn-on-a-vps.md)). `-public-host` accepts an external port (`hub.example.org:8443`) that invite links use; Settings shows TURN status and the router port forwards.
- Hardening for internet exposure: the TURN relay refuses internal-range peers (except connected apps) and limits allocations; the server limits sign-in attempts and needs passwords of at least 12 characters; the app API rate limits WebSocket messages, pairing and invite redemption ([server-configuration.md](guides/server-configuration.md#turn-security)).
- Diagnostics: overlay split into Emulation and Streaming (F3), connection type (direct / relay) with the reason per viewer for a relayed path, target bitrate, RTT in a diagnostics tab (DataChannel `fb-diag`, [protocol](../protocol/datachannel.md)); ICE is logged per connection. The host adapts the encoder bitrate to the worst viewer (AIMD). During speed-up viewers get evenly spaced base-rate frames. `UZUME_FORCE_RELAY=1` (CLI `--force-relay`) forces the relay for testing.
- Online list and notifications (0.23, [ADR 0033](adr/0033-together.md) D1, D2): the AppNav ONLINE group lists the people (not devices) who are online on the server, with "Playing <game>" or "Online"; "Watch" appears when they share a Session you may see, "Invite" when you share a Session or are in a run they are not in. The bell in the AppNav keeps the last 50 news of this server (Session invites, Sessions that start, run invites and run status changes by others, app updates, server problems for admins) with a click action (Watch, Open run, What's new, Open status); opening it marks all read. Settings › This PC › Notifications sets per kind Toast or List only, "Quiet in fullscreen" (only mentions toast) and "Sound for toasts"; toasts (max 3, 6 s) show bottom left, in game on the stage. Everything is derived from existing WSS events, in memory only.
- Connection check (Settings › Hubs or Diagnostics): server, STUN, TURN relay, NAT type, WebRTC test with a plain-language result.
- GPU paths: on NVIDIA a shared hardware-rendered Session hands the core's OpenGL texture to NVENC through CUDA-GL interop ([ADR 0019](adr/0019-gpu-direct-nvenc.md)); on Windows AMD (`h264_amf`) and Intel (`h264_qsv`) use an OpenGL to D3D11 bridge ([ADR 0027](adr/0027-gpu-paths.md); verified only locally). On Windows the same encoders take the frames of Vulkan games (a shared Vulkan texture with a keyed mutex into FFmpeg D3D11 frames; NVIDIA uses `h264_nvenc` with D3D11 frames there, [ADR 0034](adr/0034-linux-app-and-vulkan.md) D9). Any problem falls back to the readback path without stopping the Session; `UZUME_DISABLE_GPU_ENCODE=1` turns it off, and the diagnostics host line shows `· GPU-direct` or `· readback (GPU-direct off)`. The Windows FFmpeg build enables the NVENC, QSV and AMF H.264 encoders (selected at runtime, software H.264 as fallback).

## Emulation, systems and cores

- Local emulation with libretro cores: video, audio via Qt Multimedia, keyboard, touch via mouse. Core options per global/system/game level (game > system > global; locked options are hidden); per game: core choice, speed-up, reset. The Emulation page has no preselected core and shows BIOS rows only where firmware applies.
- OpenGL hardware rendering for cores that offer it (melonDS DS: OpenGL renderer and internal resolution, applied on next start, default Software). Frames are read back to the CPU by default so Sessions work unchanged. `UZUME_DISABLE_HW_RENDER=1` forces the software path; the CLI has no hardware rendering.
- Vulkan hardware rendering next to OpenGL for cores that offer it (Azahar): selectable per system or game (`uzume.renderer`, `UZUME_RENDERER`), frames are read back like OpenGL ones (on Windows the game view and a shared Session can skip the readback, see below); no Vulkan device means software fallback; a core that needs a newer Vulkan version than the system offers, or whose Vulkan context cannot be created, starts with OpenGL instead (the reason is in the diagnostics).
- Settings › Emulation: a "Renderer" row (OpenGL | Vulkan, default OpenGL, tag "Next start") for cores that offer both (3DS/Azahar); stored per system and per game, Reset removes it; DS and one-screen software systems have no Renderer row.
- Zero-copy game view ([ADR 0027](adr/0027-gpu-paths.md)): on Windows with Qt Quick on D3D11 the emulation thread blits hardware frames (OpenGL, and Vulkan through external memory) into shared D3D11 textures that the game view draws; readback runs only while a shared Session needs pixels. Any failure falls back to readback; `UZUME_DISABLE_ZERO_COPY=1` turns it off.
- Picture options (Emulation › Picture, per global/system/game level, applied live): Integer scaling (Off keeps the fit that prefers whole factors when they use the space well; On always uses whole factors and may leave borders) and Aspect ratio Core / 4:3 / Stretch (4:3 per screen on two-screen systems; Stretch fills the area). Local Multiview tiles follow them.
- Screen layouts of two-screen systems (NDS and 3DS, in game and as defaults): Stacked, Side by side, Large top / small bottom (the top screen at twice the size on the left, the bottom screen at 1x on its right, bottom edges aligned), Top screen only and Bottom screen only, plus "Swap screens" (the bottom screen is drawn where the top one would be; stacked, side by side and large only). F7 (Controllers > Hotkeys, "Screen layout") opens the Layout menu under the header button with the five layouts, Swap screens (Shift+F7 toggles it directly) and "Bottom screen in its own window"; in fullscreen, where there is no header, F7 picks the next layout. Gamepad Select + Right (default, configurable) cycles through the layouts. Every change shows a toast ("Layout: Side by side"); the keys never reach the game, and single-screen systems have no layout menu and ignore the keys. Layouts follow Integer scaling and Aspect ratio, and the touch screen works wherever the bottom screen is drawn (no touch while it is hidden). The in-game choice applies to the running game only; the start values are the Emulation options "DS and 3DS screen layout" (`uzume.screen_layout`), "Swap screens" (`uzume.screen_swap`) and "Bottom screen in its own window" (`uzume.bottom_window`) at global, system or game level. Watched Sessions with two stacked screens get the same layouts and swap.
- Bottom screen in its own window (local game only): a second window shows only the bottom screen, scaled with the picture options; mouse and touch there press the touch screen, keys act as in the game window (hotkeys, Esc opens the Quick menu). Move it to another monitor; position, size and monitor are remembered on this PC (not per game). While it is open the game view shows the top screen only; closing the window or leaving the game turns the mode off. The window always draws the readback picture, so the readback keeps running while it is open even when the game view uses the zero-copy display (ADR 0027).
- Per-game settings (0.19): the game page's Settings tab and the in-game "⋯" menu item show the tabs Picture, Controls, Speed-up and Core. Each row shows "Uses your default (X)" or "Changed for this game" with a per-row reset, plus Reset all; changes go into the game level of the local settings (game > system > global) and a reset returns to the system or global value. Live in a running game: the picture options (such as Integer scaling and Aspect ratio), and the screen layout and speed-up speed, which the dialog shows with their live value and sets on the running game; everything else (core and core options, swap, bottom window, other speed-up options, controller profiles) applies from the next start (badge "applies on next start"). The dialog is built around the reusable `GameSettingsContent`. Controller profiles use the options `uzume.pad_profile` (player 1's gamepad) and `uzume.keyboard_profile` at system and game level (also on the Emulation page): they are temporary, the device assignment is unchanged, and a deleted profile is listed as missing and the device's own profile is used.
- Ready check and shared pause (0.23, [ADR 0033](adr/0033-together.md) D3): the "⋯" menu and the Quick menu (group Together) offer "Ready check…" and "Pause for everyone" (Shift+Esc), enabled while the running game has a scope: its run, else the Session you share, else the Session you watch. One click starts a check (no dialog); every member gets a card on the stage (also on the run board of an active run, with a "Ready check" button) with the starter, one row per person (Waiting / Ready / Not yet), the seconds left (30) and Ready (1, pad A) / Not yet (2, pad B); the starter can cancel. When all are ready the card closes with the toast "Everyone is ready"; cancelled and expired checks close it too. A pause for everyone pauses the game of every run member (in a Session the host's game; viewers see the host paused state) and shows "<name> paused for everyone" with Resume until it is resumed; it resumes only a game it paused itself, never one you paused by hand. Messages: `ready_check_*`, `pause_request`, `ready_check`, `pause_state` (feature `together_v1`), in memory only.
- Chat and panel tabs (0.23, [ADR 0033](adr/0033-together.md) D4): the side panel's tabs are Session · People · Chat · Saves (in a run Run · Chat · Saves), then plugin tabs and the Plugin console in Developer mode; the states live in Saves, which embeds the saves view. People lists the people of the Session (HOST / VIEWER tags, connection, latency and quality on each row, see the next entry) with "Ready check…" and "Invite someone…"; the Run tab shows the run and its people. The Chat tab belongs to the scope of the game (run, else the Session you share, else the one you watch) and reads "RUN CHAT · <RUN> · N PEOPLE" or "SESSION CHAT · N PEOPLE": day separators, a person colour, name and time per message, the run's events as dimmed lines, three quick replies (Down!, Gym next, Wait; Alt+1 / 2 / 3 while the composer has the focus) and a one-line composer (Enter sends, Esc gives the keys back to the game, 500 characters, the counter shows near the limit). The shortcodes :gg: :wave: :lol: :hype: :sad: :ok: show as emoji (the text stays as typed). A message you sent is dimmed until the server echoes it ("Not sent · Retry" after 15 s). Run chat is stored by the server and is still there after a restart (the last 100 messages load); Session chat is the server's ring of 200 and ends with the Session. The Chat tab shows the unread count (a dot when five or more tabs are shown); only a message that names you (@name) while the tab is closed raises a toast and a bell entry, other messages stay quiet. Messages: `chat_send`, `chat_message` (feature `together_v1`).
- Viewer role and quality per viewer (0.23, [ADR 0033](adr/0033-together.md) D5, [protocol/datachannel.md](../protocol/datachannel.md)): in a Session you are the host, a viewer, or a player (a viewer whose controller the host granted, see the next entry); a viewer watches, chats and talks, and sends input only through a granted controller. On its own row in People a viewer has a one-click Quality segmented, Auto · High · Medium · Low (Auto follows the adaptive bitrate; High 4 Mbit/s, Medium 1.5, Low 0.6 at 30 fps); the pick applies at once and is the default of this PC for the next Sessions you watch. The host keeps one encoder per quality in use (at most three; fixed tiers use software readback frames, GPU-direct stays with Auto), creates a tier on its first viewer and drops it 10 s after its last viewer left; only Auto viewers steer the adaptive bitrate, and with everybody on Auto the host runs the single adaptive encoder as before. People rows read "Direct · 18 ms · gets High" or "Relayed · 60 ms · picked Medium" (latency from a ping/pong on the data channel every 2 s); the host sees "Sending 2 streams · 3.1 Mbit/s" under the list, and the F3 diagnostics show a Stream row with the tiers in use and the viewers (viewer side: what the host serves). MCP: `session_quality`, `session_viewers`.
- Controller hand-over (0.23, [ADR 0033](adr/0033-together.md) D8, [protocol/datachannel.md](../protocol/datachannel.md)): a viewer can play along. On its own row in the People tab it has the buttons "Take over P1" and, when the host's system has two controller ports (`input.ports` in the system manifest, default 1: none of the built-in systems yet), "Play as P2". The host sees one flat card on the stage, "max wants to play as P2 · Allow · Deny" (keys 1 / 2; denied by itself after 20 s). While waiting the viewer's row says "Asked lena…" (Cancel); a denial reads "lena said no", "P1 is taken" or "lena did not answer". After Allow the viewer is a PLAYER (tag "PLAYER P2" for everybody) and its keyboard (through the keyboard profile), gamepad and, with P1, the mouse on the bottom screen are captured while its tile has the focus and travel to the host over a second data channel (`fb-input`: unordered, a frame of 21 bytes per change plus a keep-alive every 100 ms; stale and out-of-order frames are dropped, and after 500 ms without a frame the port goes neutral). The host injects them into that libretro port; a P1 take-over suspends the host's own P1 keyboard and pad (host hotkeys keep working). One holder per port; a second request is refused as "P1 is taken". The host ends it at any time: "Take back" on the card or on the People row, or Esc twice; the viewer's "Stop playing", leaving, or a lost connection ends it too. The server is not involved. MCP: `control_request`, `control_answer`, `control_release`, `control_state`, `remote_input`.
- Voice chat (0.23, [ADR 0033](adr/0033-together.md) D7): a voice room per run or Session (at most 8 people), peer to peer between the apps over WebRTC (one Opus mono audio track, 24 kbit/s, 20 ms, in-band FEC, per pair; TURN as for Sessions); the server only introduces the devices and keeps who is in the room in memory (`voice_join`, `voice_leave`, `voice_state`, `voice_mute`, `voice_signal`, `voice_room`, feature `together_v1`). The header mic control says "Join voice" before the join and then the state of the microphone in a word: Hold V (push-to-talk), Live (your name gets the speaking bars), Mic off (others see "mic off"), Muted by host (only the host can undo it), No microphone (you can still listen) and Blocked (the system refuses the microphone: Open Windows settings, on Linux the PipeWire prompt appears again). Shift+M switches the microphone on and off; push-to-talk is V (hold) or Select + R3 (hold), with voice activation the same keys switch the mic. The People tab has Join voice / Leave voice, a voice mark on every row (speaking bars, mic off, muted by host: shape and word, never colour alone), a Volume slider per person (remembered per user on this PC) and, for the owner of a Session, Mute / Unmute; the Multiview tiles show the marks too, and "<name> joined voice" is a toast. While someone else speaks, game and tiles are halved when "Lower game volume while someone speaks" is on. Settings › This PC › Voice: Microphone (with the live level and the voice-activation threshold line; a click on the bar moves it), Talk (Push-to-talk, the default, or Voice activation), the key, Noise suppression (speexdsp noise suppression and echo cancellation against what your speakers play), ducking and Join voice automatically (runs you play and invite-only Sessions; otherwise one click). Headphones are recommended. MCP: `voice_state`, `voice_join`, `voice_leave`, `voice_mic`, `voice_inject`.
- In-game control bar, Quick menu and Game tab ("Uzume 7", [decisions](design/uzume/decisions.md#sheet-7--in-game-redesign-2026-10-26)): every header control has a frame and shows its value ("» Speed-up OFF · 2×" as a split button with the speed menu, "Sound 5 %", "Screens <layout>", Panel Shown / Hidden, Fullscreen, Pause / Resume as the one primary); "⋯" holds Diagnostics (F3), Screenshot (F12), Hotkeys, Settings for this game…, Report a problem… and Reset game…. Narrow windows drop words before values, then move Fullscreen and Screens into "⋯". Esc, the Pause button and Start on a pad open the Quick menu instead of a pause dialog: Resume, the groups Game / Play / Together / Help and Quit game…; pad A chooses, B resumes. CLI: `fetch-core <system-id>`. Handshake feature `cores_v2` lists the installed cores per system (`default_core_id`, `cores`).

## Accounts and administration

- Setup: the first admin is created from the app with a setup code (`POST /api/v1/setup`, printed at start and by `uzume-server setup-code`), or via `setup-admin`. First start in the app, join with a security code check, `uzume://join/...` invite links.
- Server commands for setup and emergencies: `setup-code`, `code` (security code of the certificate), `reset-admin`, `status`, `update`, `backup`, `restore`, `reset` on Windows, Linux and in Docker ([server-configuration.md](guides/server-configuration.md#server-commands)).
- HTTPS with a self-signed certificate (or your own); the fingerprint is logged at startup. The server renews its own certificate at startup when it is expired or expires within 30 days (`uzume-server renew-cert` on demand, or "Renew now" in Server › Settings › Network & sharing without a restart; key and certificate are written atomically); the app shows "Expires within 30 days". Own certificates are never modified.
- The app identifies a server with fingerprint confirmation on first contact (TOFU); on mismatch the connection is blocked and no credential is sent. After a certificate change the server card shows the stored and the presented fingerprint; "Trust new certificate" and then "Yes, trust this certificate" re-pin it and keep the credential (CLI: `--accept-fingerprint <sha256>`).
- Info endpoint `/.well-known/uzume` and handshake with `protocol_version`.
- Device credentials, PIN hashes and the MCP token live in the OS credential store: Windows Credential Manager, or the freedesktop Secret Service on Linux (memory only when no session bus or service exists; `UZUME_CREDENTIAL_STORE=memory` forces that).
- Accounts (`accounts_v1`, [ADR 0030](adr/0030-one-app-one-server-uzume.md) D5): every user can have a password (admins must); a new device signs in with user name and password instead of waiting for approval; several people per PC with a switch-user sheet (Ctrl+Shift+U) and an optional 4-digit PIN for this PC; My account; own device list with sign-out; admin password reset with a temporary password; no email recovery. "Confirm it's you" asks for the password before dangerous admin steps (server answer `confirmation_required`) and then carries the step out.
- Pairing of devices with Allow/Deny; issue and revoke tokens (Revoke); Delete removes a device entry for good (saves are kept). Apps below the minimum protocol version are marked "Player too old".
- Connection screen ("Where are your games?"): saved servers as rows with one Connect and a ⋯ menu, "Connect automatically when Uzume starts" (on by default after the first successful connection; an explicit off is kept), one "Another server" field with Add server and Play on this PC; a failed automatic connect stops on this screen with the error; Settings › Hubs: switch, edit, remove (with confirmation), auto-connect; the current server is marked. Credentials are in the Credential Manager on Windows; in the freedesktop Secret Service on Linux; without a session bus or service they are kept in memory only (new pairing and admin approval after every restart, see [guides/app.md](guides/app.md)).
- Admin area in the app ([ADR 0030](adr/0030-one-app-one-server-uzume.md), [design](design/uzume/accounts-and-server.md)): AppNav group SERVER for admins of a server with `admin_v1`:
  - Status: metrics, Sessions, connected apps, server log download.
  - Users: People with role, turn off/on, remove (the warning offers "Download saves…": all saves and history of the person as one zip; delete removes their devices, invites, saves and history, uploaded games stay), password reset, rename, add; Invites (single-use codes shown once with a `uzume://join/...` link, expiry 1 h / 24 h / 7 days); Devices (approve/deny/sign out/rename, assign a pending device to a user). Display names are unique.
  - Systems & cores, Saves, Library: see the sections above.
  - Plugins: uploaded plugins, official index, upload with permission ticks. Reports: inbox, attachments, mark as seen. Runs get admin actions.
  - Server screen (sidebar item "Server", admins with `admin_v1`; header with server name and address · Online/Offline · version; tabs Overview, People, Games, Systems & cores, Plugins, Reports, Settings): Games holds rescan folders, Upload ROM, the import folder and "Members can add games". Server › Settings pages: General, Network & sharing (port, embedded TURN, public host, relay range, save retention, external TURN, restart line), Sign-in policy, Updates, Backups, Storage, Diagnostics. Storage page (admin, `GET /api/v1/admin/storage`): disk and backup disk, sizes of games, saves and snapshots, save states, screenshots (also the largest per user and game), cores and firmware, and backups; clean-up after "Confirm it's you" of automatic save versions older than 90 days (never manual snapshots, current saves or slots with an open conflict), upload leftovers idle for more than 7 days and core versions no system uses. Saved settings win over `server.env`; changes that need it are applied by a restart the server triggers itself (ports below 1024 only via `install-server.sh --port`).
  - What's new after an update and a setup assistant. Appearance (Dark / Light / System) is in Settings › This PC.
- App identity: the Uzume logo is the window/taskbar icon, the Windows executable icon and the installer icon; the sidebar user block shows the server user name above the device name.

## Discord Rich Presence

- Optional, off by default: Settings › This PC › My account › "Show what I play on Discord" (local app setting `discord_presence` in `settings.json`; it is not synced and not tied to a server).
- The app talks to the local Discord client over its IPC (`discord-ipc-0` to `-9`: unix socket under `$XDG_RUNTIME_DIR`, `$TMPDIR`, `$TMP`, `$TEMP` or `/tmp`, named pipe on Windows; Qt `QLocalSocket`, no SDK). Public application ID `1564614458993545296`.
- Shown while a game runs: game title, system name (plus "· Session" while the game is shared, or the run name in a run) and the start time. Never the server address, other people, ROM paths or anything else private.
- Updates on game start, game end, Session and run change, at most one every 15 s (the latest state wins); the activity is cleared at once when the game ends or the switch is turned off.
- If Discord is not running nothing happens: the app retries every 30 s while a game runs, never blocks the UI and logs one info line (`uzume.discord`) per state change. MCP `status` shows `discord` (enabled, connected, last details and state).

## Plugins and runs

- Plugin runtime ([guide](guides/plugin-api.md), [ADR 0023](adr/0023-plugins.md)): sandboxed Lua 5.4 plugins read game memory by virtual address (memory maps from the core, snapshots after the emulated frame) and use native helpers for game-file formats. Install from the server, from a folder, or link a folder with live reload (developer mode); Settings › Plugins and an in-game Plugin console. Developer console (Developer mode): log with level filters and counts, permissions, reload with state kept in `fb.store`/`fb.run`, reload on file change, a read-only memory viewer, "Load unpacked..."; a plugin pauses after 3 errors within 10 s ([guide](guides/plugin-api.md#developer-mode)).
- Plugin UI: declarative blocks and a map view in the in-game tab, HUD, Multiview tile strip, run tab (`screen` slot; `fb.ui.open("screen")` selects it), game detail section, toasts and plugin hotkeys (Alt+1..9 panel tabs, F4 hides HUD widgets). Plugins have no sidebar entries. Plugin UI language: Settings › Plugins: Auto | English | Deutsch (Auto uses the 3DS system language for 3DS games).
- Server plugins ([publishing](guides/plugin-publishing.md)): the server offers `.uzplugin` files (admin upload with permission ticks, `uzume-server import-plugins`, official signed plugin index by default, `-plugin-index-url none` for offline servers); plugins signed with the Uzume key show as Official, others as Unverified or Local; apps install them from the server with a SHA-256 pin or from a file. Official plugin ids are `uzume.soullink-core` and `uzume.soullink`.
- Runs (`runs_v1`, `runs_v2`): the server stores runs (0 to 8 plugins, participants, per-player and per-plugin state, event log, plugin boards) and fans them out over WSS. A run carries `save_slot` (`run-` + first 8 hex of the run id); each person gets Run: <Name> and Main is not touched.
- Runs screen: always in the navigation when the server has `runs_v1`; "Start a run" offers Rules "None" (needs `runs_v2`) or an installed run plugin, plugin run settings (`run_settings`, for example mode) only when a plugin is chosen, required plugins are included automatically; invites with plugin consent, "Play run" with the exact server plugin versions and a per-run save slot; the game picker keeps the library games whose system and server-known game code fit every plugin of the run. The run view has the tabs Board (participants with their save slot), Recap, Log and one tab per run plugin, last (plugin section `ui.run`, read-only). Plugins use `fb.run` (permission `run.state`). Admin actions: Start now/without, Pause/Resume, Finish, Archive, Delete, resend/remove invites.
- Run recap (0.22, design 4jh-app-2): the Recap tab of every run, also finished ones, pages the whole event log and the run's screenshots and shows four tiles (CATCHES, LOST, BADGES with a split per person, PLAY TIME with the days) and the Lanes block: one lane per person, glyphs ■ catch, ✕ lost, ◆ badge, □ note, ▣ screenshot by day. Plugins map their event types to glyphs in the manifest field `recap` ([plugin API](guides/plugin-api.md#run-recap)); events of plugins that are not installed, or without a mapping, are not shown. The core events `rules.changed`, `cheat.enabled`, `cheat.disabled`, `memory.write` and `state.loaded` appear as notes and are not counted. Without play time from the server the fourth tile shows the elapsed days. "Export" saves a PNG of the recap or one self-contained HTML file (no external resources); "Share link" copies `uzume://run/<server>/<run id>/recap`, which opens the recap in an app signed in to that server. Debug MCP tool `run_recap`.

## Game variants and the randomizer

0.21, [ADR 0031](adr/0031-game-variants-and-randomizer.md), guides: [app](guides/app.md#randomize-a-game), [server](guides/server-configuration.md#tools), [plugin API](guides/plugin-api.md#variants-variantsbuild). Built and tested with a test engine; the real engine on a real game is verified only by Fabio, and 3DS updates are not handled yet (open).

- A **variant** is a library game plus a recipe: engine and version, settings string, seed, and the pin of the base (SHA-256 of the base dump for GB to NDS, the title ID for 3DS). The server stores only the recipe (`variants_v1`), never ROM data, patches or spoiler logs; the owner alone sees the settings and the seed. The name is unique per person and game.
- Every variant plays in its **own save slot** `var-<first 8 hex of the variant id>`; Main is never touched, and starting a variant starts exactly that variant, never the original dump. A run variant plays in the run's slot "Run: <Name>". Deleting a variant asks whether to keep the saves (default; the recipe stays, "Build it again") or delete the slot too, with the same rules as deleting a slot.
- **Randomize…** sits next to Play on the game page when an enabled plugin with the permission `variants.build` registered the game's system and game code (the plugin Randomizer does for Gen 1 to 7). The dialog offers a preset, "Custom" (a pasted settings string, checked for form and version), an optional seed (off: Uzume picks one), an optional spoiler log, and a name. The same settings string and seed build the same world on every PC; the string carries its settings version and the engine upgrades older strings itself.
- The **engine** (UPR FVX, GPL-3.0, Java with its own runtime) is offered by the server from Server › Tools and downloaded once per PC from that server ([tools catalog](guides/server-configuration.md#tools)); the app checks the SHA-256 and unpacks it into `<data>/cache/tools/`. It runs only on the user's PC, as a child process with a fixed argument list and no shell, with a time limit (3 minutes, 3DS 15), a Java heap of 1 GB (3DS 4 GB) and a check for free memory and disk space; progress is an estimate, a build can be cancelled and then keeps nothing. Only the engine's own error and warning lines are kept for diagnostics.
- **Output:** GB to NDS give a whole ROM in the local variant cache `<data>/cache/variants/` (limit 8 GB by default, least recently played dropped first; the recipe stays, so a dropped variant rebuilds when played, "needs rebuild"). The base file must match the pinned SHA-256; a different dump gives a clear state with "Build anyway" instead of silently another world. 3DS gives a LayeredFS folder that is copied to `<save dir>/Azahar/load/mods/<title id>/` of the variant's slot before the start (and removed again for Main and other slots); save sync packs only `sdmc`, so the mod never travels to the server. `fb.rom.*` of a plugin reads the started file, so SoulLink Core sees the randomized data.
- **Spoilers stay hidden:** nothing in the app shows what was randomized. The spoiler log is off by default, opens only from the variant's menu after a confirm, and for a run only after the run ends and only the own one. Error details carry no creature, item or trainer names.
- **Runs:** New run has a Randomizer section (off; "Each person gets their own"; "Same world for everyone"), with preset or custom string, the engine version (offered versions only) and "Allow own variants". The server creates a run seed that nobody receives, pins the engine version and the creator's base (SHA-256, or the 3DS title) and shows the run only `mode`, preset, engine version and `allow_own`. On joining, each person chooses the run's variant or, if allowed, an own variant of the same game and engine version (409 `own_variants_off`, `own_variant_mismatch` otherwise). `GET /runs/{id}/variant` gives a joined participant the recipe: the seed is the run seed for "same world", and for "each" the first 8 bytes of `SHA-256(<run seed> ":" <user id>)` as a non-negative 63-bit integer, so no two people share a world and nobody can compute another's. Before the first start of the run the app builds the person's variant ("Building your variant"), reports `not_built`, `building` or `ready` to the server, and the dialog can start the run as soon as it is ready. The run board shows only "Run variant" or "Own variant" per person and a Randomizer block (preset, engine version); engine versions used by a variant or an unfinished run cannot be removed from the server.
- **Storage:** Settings › Folders & storage lists the variant cache with a size limit, "Free space" and "Remove variants not played for 30/60/90 days"; both only remove the copies on this PC, recipes and saves stay on the server.
- Debugging: the MCP server ([Claude debugging](guides/app.md#claude-debugging-mcp)) has the tools `tools_list`, `tool_prepare`, `variants_list`, `variant_presets`, `variant_build`, `variant_status`, `variant_cancel`, `variant_delete`, `variant_files` (name, size and SHA-256 of the built files, to compare two builds), `variant_start` and `run_variant_build`.
